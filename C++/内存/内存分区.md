在C++程序运行时，内存会被划分为五个区域，分别是栈区、堆区、全局/静态区、常量区和代码区
![[C++/内存/assets/2e7a1d647be9f5e9afb035a65fba1124_MD5.jpg]]
- **栈(Stack)**:用于存储局部变量和函数调用的上下文。栈的内存分配是自动的，由编译器管理。
- **堆(Heap)**:用于动态内存分配。程序员可以使用malloc 等操作符或函数从堆上分配内new存，并使用 delete、free释放内存。
- **全局/静态存储区(Global/StaticStorage)**:存储全局变量和静态变量，包括:
	- **数据段**:存储初始化的全局变量和静态变量。
	- **BSS段**:存储未初始化的全局变量和静态变量。
- **常量存储区(ConstantData)**:存储程序中的常量数据，如字符串字面量。
- **代码段(CodeSegment或TextSegment)**:存储程序的可执行代码和函数的二进制指令。

## 堆和栈的区别
堆(Heap)和栈(Stack)是程序运行时两种不同的内存分配区域。
内存分配:

1. 栈
- 是由编译器自动管理的，用于存储局部变量和函数调用的上下文信息。
- 栈上的对象在定义它们的块或函数调用结束后自动销毁。
- 栈的内存分配和释放速度很快，因为栈的内存管理是连续的，不需要搜索空闲内存。
1. 堆
- 由程序员手动管理的，用于存储动态分配的对象。
- 堆上的对象需要程序员手动释放，否则可能导致内存泄漏。
- 堆的内存分配和释放速度通常比栈慢，因为可能需要搜索合适的内存块，并且涉及内存碎片整理。
大小限制:
栈的大小通常有限制，远小于堆的大小，且在不同系统和编译器中可能不同。
堆的大小通常很大，受限于系统可用内存。

3.使用场景:
栈主要用于存储函数参数、局部变量等。
堆用于存储生存期不受限于单个函数调用的对象，如使用new或malloc分配的对象。

#### 栈分配: TFixedAllocator

**What - 是什么**
`TFixedAllocator` 是 UE5 中的固定大小内联分配器，将数据直接存储在容器结构内部（栈上），而不是堆上。

来源: [ContainerAllocationPolicies.h:1195-1288](E:\Epic Games\UE_5.4\Engine\Source\Runtime\Core\Public\Containers\ContainerAllocationPolicies.h)

```cpp
template <uint32 NumInlineElements>
class TFixedAllocator
{
    template<typename ElementType>
    class ForElementType
    {
        // 数据直接嵌入在容器中，存储在栈上
        TTypeCompatibleBytes<ElementType> InlineData[NumInlineElements];

        // 始终返回内联数据的指针，不会进行堆分配
        FORCEINLINE ElementType* GetAllocation() const
        {
            return GetInlineElements();
        }

        // 强制大小限制，超出会触发断言
        void ResizeAllocation(SizeType PreviousNumElements, SizeType NumElements, SIZE_T NumBytesPerElement)
        {
            check(NumElements >= 0 && NumElements <= NumInlineElements);
        }

        // 始终返回 false - 没有堆分配
        bool HasAllocation() const { return false; }
    };
};
```

**原理**:
- 使用 `TTypeCompatibleBytes` 在编译期预留固定大小的内存空间
- 数据与容器对象一起分配，无需额外的堆内存
- 强制执行大小限制，超出会导致程序崩溃（check 断言）

**Why - 为什么使用**

优势:
1. **零堆分配开销** - 所有内存都在栈上，避免 malloc/free 调用
2. **缓存友好** - 数据与容器紧密排列，提高 CPU 缓存命中率
3. **性能可预测** - 在热点循环中无分配/释放开销
4. **内存效率** - 无指针间接访问，无 malloc 元数据开销
5. **编译期保证** - 大小在编译期确定，类型安全

劣势:
1. **硬性大小限制** - 超出容量会崩溃，不会自动扩展
2. **占用栈空间** - 大型分配可能导致栈溢出（栈通常只有 1-8MB）
3. **无灵活性** - 无法动态增长
4. **空间浪费** - 如果只用 1 个元素但分配了 64 个，会浪费 63 个槽位

**How - 如何使用**

#### 堆分配: TSizedHeapAllocator

**What - 是什么**
`TSizedHeapAllocator` 是 UE5 中的动态堆分配器，用于大小不确定或需要动态增长的数据。

来源: [ContainerAllocationPolicies.h:601-805](E:\Epic Games\UE_5.4\Engine\Source\Runtime\Core\Public\Containers\ContainerAllocationPolicies.h)

```cpp
template <int IndexSize, typename BaseMallocType = FMemory>
class TSizedHeapAllocator
{
    void ResizeAllocation(
        SizeType PreviousNumElements,
        SizeType NumElements,
        SIZE_T NumBytesPerElement)
    {
        // 使用 FMemory::Realloc 在堆上动态分配/调整内存
        if (Data || NumElements)
        {
            Data = (FScriptContainerElement*)BaseMallocType::Realloc(
                Data,
                NumElements * NumBytesPerElement,
                Alignment
            );
        }
    }

    // 支持无限增长
    bool HasAllocation() const { return !!Data; }
};

using FHeapAllocator = TSizedHeapAllocator<32>;  // TArray 的默认分配器
```

**原理**:
- 使用 `FMemory::Realloc` 在堆上分配内存
- 支持动态增长和收缩
- 数据存储在堆上，容器只保存指针

**Why - 为什么使用**

优势:
1. **动态大小** - 可以根据需要无限增长
2. **不占用栈空间** - 适合大型数据集
3. **灵活性** - 支持任意大小的数据

劣势:
1. **分配开销** - 每次增长都需要调用 malloc/realloc
2. **内存碎片** - 频繁分配/释放可能导致堆碎片
3. **缓存不友好** - 数据不与容器连续存储

**How - 如何使用**

这是 `TArray` 的默认分配器，用于所有大小不确定的动态数组:

```cpp
TArray<int32> DynamicArray;  // 默认使用 FHeapAllocator
DynamicArray.Add(1);         // 堆分配
DynamicArray.Add(2);         // 可能触发 realloc
```

**为什么用**: 当数据大小无法预测或可能很大时，必须使用堆分配。

| 分配器 | 内存位置 | 大小 | 性能 | 使用场景 |
|--------|---------|------|------|---------|
| **TFixedAllocator** | 栈 | 固定 | 最快 | 已知边界的小集合（三角形顶点、悬挂参数） |

## new 和 malloc 的区别
1. 语法层面:
new是C++的操作符，可以直接用来分配对象或数组。
malloc是一个函数，通常需要包含头文件，并且只分配原始内存。
2. 类型安全:
new是类型安全的，它会根据分配的对象类型进行正确的内存分配和构造函数调用。
malloc 不是类型安全的，它只分配原始内存，不调用构造函数。返回类型是void*，需要强制类型转换为具体的指针类型。
3. 构造与析构:
使用new 分配的对象在对象生命周期结束时需要使用 delete 来释放，delete 会自动调用对象的析构函数。
使用 malloc 分配的内存需要使用 free 来释放，free 不会自动调用析构函数，因此如果分配的是对象数组，需要手动调用析构函数。
4. 异常安全性:
new 在分配失败时会抛出std::bad_alloc 异常。
malloc在分配失败时返回 NULL指针
5. 管理机制:
C++中的new和delete通常由编译器实现，可能包含一些额外的内存管理机制。
C语言的malloc 和free由C标准库提供，与编译器无关。
总结来说，new和malloc都是动态内存分配的手段，但new提供了类型安全和构造/析构的自动化，而malloc则提供了更底层的内存分配方式，需要手动管理构造和析构。在C++中，推荐使用new来分配对象，以保持类型安全和自动化的资源管理。

### UE5 中的 malloc 和 new 使用示例

#### malloc/free: FMemory 系统

**What - 是什么**
UE5 使用 `FMemory::Malloc/Free` 封装底层的 C 风格内存分配，而不是直接使用 C++ 的 new/delete。

来源: [MallocAnsi.cpp:24-142](E:\Epic Games\UE_5.4\Engine\Source\Runtime\Core\Private\HAL\MallocAnsi.cpp)

```cpp
// malloc 实现 - 平台特定的内存分配
void* AnsiMalloc(SIZE_T Size, uint32 Alignment)
{
#if PLATFORM_USES__ALIGNED_MALLOC
    void* Result = _aligned_malloc(Size, Alignment);
#elif PLATFORM_USE_ANSI_POSIX_MALLOC
    void* Result;
    if (UNLIKELY(posix_memalign(&Result, Alignment, Size) != 0))
    {
        Result = nullptr;
    }
#else
    // 手动处理对齐
    void* Ptr = malloc(Size + Alignment + sizeof(void*) + sizeof(SIZE_T));
    void* Result = nullptr;
    if (Ptr)
    {
        Result = Align((uint8*)Ptr + sizeof(void*) + sizeof(SIZE_T), Alignment);
        *((void**)((uint8*)Result - sizeof(void*))) = Ptr;
        *((SIZE_T*)((uint8*)Result - sizeof(void*) - sizeof(SIZE_T))) = Size;
    }
#endif
    return Result;
}

// free 实现 - 释放原始内存
void AnsiFree(void* Ptr)
{
#if PLATFORM_USES__ALIGNED_MALLOC
    _aligned_free(Ptr);
#elif PLATFORM_USE_ANSI_POSIX_MALLOC || PLATFORM_USE_ANSI_MEMALIGN
    free(Ptr);
#else
    if (Ptr)
    {
        free(*((void**)((uint8*)Ptr - sizeof(void*))));
    }
#endif
}

// realloc 实现 - 调整内存大小
void* AnsiRealloc(void* Ptr, SIZE_T NewSize, uint32 Alignment)
{
    void* Result;
#if PLATFORM_USES__ALIGNED_MALLOC
    if (Ptr && NewSize)
    {
        Result = _aligned_realloc(Ptr, NewSize, Alignment);
    }
    else if (Ptr == nullptr)
    {
        Result = _aligned_malloc(NewSize, Alignment);
    }
    else
    {
        _aligned_free(Ptr);
        Result = nullptr;
    }
#elif PLATFORM_USE_ANSI_POSIX_MALLOC
    if (Ptr && NewSize)
    {
        SIZE_T UsableSize = malloc_usable_size(Ptr);
        if (UNLIKELY(posix_memalign(&Result, Alignment, NewSize) != 0))
        {
            Result = nullptr;
        }
        else if (LIKELY(UsableSize))
        {
            FMemory::Memcpy(Result, Ptr, FMath::Min(NewSize, UsableSize));
        }
        free(Ptr);  // 释放旧内存
    }
#endif
    return Result;
}
```

**原理**:
- 直接调用平台的 malloc/free 函数（Windows 用 `_aligned_malloc`，POSIX 用 `posix_memalign`）
- 只分配原始内存，不调用构造函数或析构函数
- 支持自定义对齐要求

**Why - 为什么 UE5 使用 malloc 而不是 new**

优势:
1. **自定义分配器支持** - `FMemory` 可以重定向到自定义分配器（内存池、LLM 追踪）
2. **对齐控制** - 直接支持对齐参数，对 SIMD 和缓存行对齐至关重要
3. **性能** - 对于 POD 类型，避免了 C++ 构造/析构开销
4. **平台抽象** - 统一的接口封装不同平台的内存分配差异
5. **内存追踪** - 可以在分配/释放时插入追踪代码

劣势:
1. **无类型安全** - 返回 `void*`，需要手动类型转换
2. **无自动构造/析构** - 必须手动管理对象生命周期
3. **容易出错** - 忘记释放导致内存泄漏

**How - 如何使用**

## delete和free的区别
1. 语法:
delete是C++中的关键字，用于释放由new 分配的对象。
free是C语言中的函数，通常包含在<stdlib.h>头文件中，用于释放由malloc分配的内存。
2. 对象销毁:
当使用 delete 释放对象内存时，C++ 编译器会自动调用对象的析构函数，释放与对象相关的资源，并执行对象的清理工作。
free 仅释放内存，不调用析构函数。因此，如果使用 malloc 分配了对象的内存，需C++要手动调用析构函数后再调用 free
3. 数组处理:
如果是数组，C++提供了delete[]来释放整个数组的内存，而C语言中仍然使用free，没有区分单个对象和数组。
4. 返回值:
free 没有返回值，即使内存释放失败，也不会反馈任何信息。
delete之后，指针依然保存着原来的地址，这个状态被称为悬空指针，在释放指针后，立刻手动置为nullptr，避免出现悬空指针导致访问已释放的内存。
5. 类型检查:
delete 进行类型检查，确保删除的对象类型与new 分配时的类型一致。
free 不进行类型检查，因为它只处理void* 类型的指针。
总结来说，delete和free都是用来释放动态内存的，但它们分别用于C++和C语言中的内存管理。delete适用于C++对象，会自动调用析构函数;而free适用于C语言分配的内存，不涉及对象的析构。

```cpp
// free 实现 - 只释放内存，不调用析构函数
void AnsiFree(void* Ptr)
{
#if PLATFORM_USES__ALIGNED_MALLOC
    _aligned_free(Ptr);  // Windows 平台
#elif PLATFORM_USE_ANSI_POSIX_MALLOC || PLATFORM_USE_ANSI_MEMALIGN
    free(Ptr);  // POSIX 平台
#else
    if (Ptr)
    {
        // 手动对齐的情况，需要找到原始指针
        free(*((void**)((uint8*)Ptr - sizeof(void*))));
    }
#endif
}
```

**原理**:
- 直接调用平台的 `free` 函数释放内存
- 只处理内存块，不关心内存中存储的是什么类型
- 不调用任何析构函数

**Why - 为什么使用 free**

优势:
1. **性能** - 无析构函数调用开销
2. **简单** - 直接释放内存块
3. **适合 POD 类型** - 对于简单数据类型（int、float 等），无需析构

劣势:
1. **不安全** - 如果释放的是对象，不会调用析构函数，可能导致资源泄漏
2. **无类型检查** - 接受任何 `void*` 指针
3. **容易出错** - 必须与 `malloc` 配对使用

**How - 如何使用**

**使用场景 1: 容器内存释放**
来源: [ContainerAllocationPolicies.h](E:\Epic Games\UE_5.4\Engine\Source\Runtime\Core\Public\Containers\ContainerAllocationPolicies.h)

```cpp
// TArray 释放内存
~TSizedHeapAllocator()
{
    if (Data)
    {
        // 使用 FMemory::Free 释放原始内存
        // 注意：元素的析构函数已经在之前单独调用
        FMemory::Free(Data);
    }
}
```

**为什么用**: TArray 先手动调用每个元素的析构函数，然后用 `FMemory::Free` 释放整块内存，避免重复析构。

**使用场景 2: 内存池释放**
来源: [AllocatorFixedSizeFreeList.h:108-133](E:\Epic Games\UE_5.4\Engine\Source\Runtime\Core\Public\Containers\AllocatorFixedSizeFreeList.h)

```cpp
// 固定大小分配器的内存池
void Free(void *Element)
{
    --NumLive;
    FreeListNode* NewFreeElement = (FreeListNode*)Element;
    NewFreeElement->NextFreeAllocation = FreeList;
    FreeList = NewFreeElement;  // 返回到空闲链表，不释放内存
}

// 真正释放内存发生在析构函数中
~TAllocatorFixedSizeFreeList()
{
    // 释放所有内存块
    while (FreeList)
    {
        void* NextBlock = FreeList->NextFreeAllocation;
        FMemory::Free(FreeList);  // 使用 free 释放原始内存
        FreeList = (FreeListNode*)NextBlock;
    }
}
```

**为什么用**: 内存池管理原始内存块，使用 `FMemory::Free` 批量释放，无需关心对象析构。

#### delete: 对象销毁

**What - 是什么**
`delete` 先调用对象的析构函数，然后释放内存，用于销毁 `new` 创建的对象。

来源: [SharedPointer.h](E:\Epic Games\UE_5.4\Engine\Source\Runtime\Core\Public\Templates\SharedPointer.h)

```cpp
// 智能指针的引用计数控制器
template <typename ObjectType>
class TReferenceControllerBase
{
    virtual void DestroyObject()
    {
        // 调用 delete，会先调用析构函数，再释放内存
        delete GetObjectPtr();
    }

    ObjectType* GetObjectPtr() const
    {
        return Object;
    }

private:
    ObjectType* Object;
};

// 当引用计数归零时
~TSharedPtr()
{
    if (SharedReferenceCount.IsValid())
    {
        SharedReferenceCount.ReleaseSharedReference();
        // 如果这是最后一个引用，会调用 DestroyObject()
        // DestroyObject() 内部调用 delete，触发析构函数
    }
}
```

**原理**:
1. 调用对象的析构函数（清理资源、释放成员变量）
2. 释放对象占用的内存
3. 类型安全，编译期检查类型匹配

**Why - 为什么使用 delete**

优势:
1. **自动析构** - 自动调用析构函数，清理资源（文件句柄、网络连接等）
2. **类型安全** - 编译期类型检查
3. **RAII 支持** - 配合智能指针实现自动资源管理

劣势:
1. **性能开销** - 需要调用析构函数
2. **必须配对** - 必须与 `new` 配对使用
3. **悬空指针** - 释放后指针仍保留地址，需要手动置为 `nullptr`

**How - 如何使用**

**使用场景 1: 智能指针自动删除**
```cpp
// TUniquePtr 自动管理对象生命周期
{
    TUniquePtr<FMyObject> Obj = MakeUnique<FMyObject>();

    // 使用对象
    Obj->DoSomething();

    // 离开作用域时，TUniquePtr 自动调用 delete
    // 1. 调用 FMyObject::~FMyObject() 析构函数
    // 2. 释放内存
}
```

**为什么用**: 自动管理对象生命周期，避免忘记 delete 导致内存泄漏。

**使用场景 2: 共享所有权**
```cpp
// TSharedPtr 引用计数管理
TSharedPtr<FGameObject> SharedObj = MakeShared<FGameObject>();

{
    TSharedPtr<FGameObject> AnotherRef = SharedObj;  // 引用计数 +1

    // 使用对象
    AnotherRef->Update();

    // AnotherRef 离开作用域，引用计数 -1
}

// SharedObj 离开作用域，引用计数归零
// 自动调用 delete，触发 FGameObject::~FGameObject()
```

**为什么用**: 多个系统共享对象时，使用引用计数自动管理生命周期。

**使用场景 3: 数组删除**
```cpp
// 错误示例：使用 delete 释放数组
int* arr = new int[10];
delete arr;  // 错误！只调用一次析构函数

// 正确示例：使用 delete[] 释放数组
int* arr = new int[10];
delete[] arr;  // 正确！调用 10 次析构函数
```

**为什么用**: `delete[]` 会为数组中的每个元素调用析构函数，而 `delete` 只调用一次。

#### delete vs free 对比

| 特性 | free (FMemory::Free) | delete (智能指针) |
|------|---------------------|------------------|
| **析构函数** | 不调用 | 自动调用 |
| **类型检查** | 否 (void*) | 是 |
| **配对要求** | 必须与 malloc 配对 | 必须与 new 配对 |
| **数组处理** | 无区别 | 需要 delete[] |
| **悬空指针** | 不处理 | 智能指针自动置空 |
| **使用场景** | POD 类型、容器内部 | 对象管理、RAII |

#### UE5 的内存管理策略

**分离构造和分配**:
```cpp
// TArray 的做法：分离构造和内存分配
void* Memory = FMemory::Malloc(sizeof(FMyObject) * Count);  // 分配内存

for (int i = 0; i < Count; ++i)
{
    new (Memory + i * sizeof(FMyObject)) FMyObject();  // 放置 new，调用构造函数
}

// 销毁时：分离析构和内存释放
for (int i = 0; i < Count; ++i)
{
    ((FMyObject*)Memory)[i].~FMyObject();  // 手动调用析构函数
}

FMemory::Free(Memory);  // 释放内存
```

**为什么这样做**:
1. **性能** - 一次分配整块内存，避免多次 malloc
2. **灵活性** - 可以单独控制构造和析构时机
3. **内存池** - 可以重用内存，无需频繁分配/释放

**实际应用示例**:
来源: [AllocatorFixedSizeFreeList.h](E:\Epic Games\UE_5.4\Engine\Source\Runtime\Core\Public\Containers\AllocatorFixedSizeFreeList.h)

```cpp
// 固定大小内存池
class TAllocatorFixedSizeFreeList
{
    void Grow(uint32 NumElements)
    {
        // 一次性分配多个元素的内存
        uint8* RawMem = (uint8*)FMemory::Malloc(AllocationSize * NumElements);

        // 构建空闲链表
        FreeListNode* NewFreeList = (FreeListNode*)RawMem;
        for (uint32 i = 0; i < NumElements - 1; ++i, NewFreeList = NewFreeList->NextFreeAllocation)
        {
            NewFreeList->NextFreeAllocation = (FreeListNode*)(RawMem + (i + 1) * AllocationSize);
        }

        NewFreeList->NextFreeAllocation = FreeList;
        FreeList = (FreeListNode*)RawMem;
    }

    void* Allocate()
    {
        if (!FreeList)
        {
            Grow(BlockSize);  // 内存不足时扩展
        }

        void* RawMem = (void*)FreeList;
        FreeList = FreeList->NextFreeAllocation;
        ++NumLive;

        return RawMem;  // 返回原始内存，由调用者使用放置 new 构造对象
    }

    void Free(void* Element)
    {
        --NumLive;
        FreeListNode* NewFreeElement = (FreeListNode*)Element;
        NewFreeElement->NextFreeAllocation = FreeList;
        FreeList = NewFreeElement;  // 返回到空闲链表，不释放内存
    }
};
```

**为什么用内存池**:
1. **减少碎片** - 固定大小分配，避免堆碎片
2. **提升性能** - 避免频繁的 malloc/free 系统调用
3. **缓存友好** - 连续分配的内存提高缓存命中率

## UE5 内存管理最佳实践

### 1. 选择合适的分配器

**决策树**:
```
数据大小已知且很小（< 64 字节）？
  └─ 是 → 使用 TFixedAllocator<N>（栈分配）
  └─ 否 → 数据通常小但偶尔大？
      └─ 是 → 使用 TInlineAllocator<N>（混合分配）
      └─ 否 → 使用 FHeapAllocator（堆分配）

对象需要自动生命周期管理？
  └─ 是 → 单一所有者？
      └─ 是 → 使用 TUniquePtr
      └─ 否 → 使用 TSharedPtr
  └─ 否 → 使用 FMemory::Malloc/Free
```

### 2. 内存分配模式对比

| 模式 | 适用场景 | 示例 |
|------|---------|------|
| **栈分配** | 小型、固定大小、短生命周期 | 三角形顶点、临时计算缓冲区 |
| **堆分配** | 大型、动态大小、长生命周期 | 游戏对象数组、资源缓存 |
| **内存池** | 频繁分配/释放、固定大小 | 粒子系统、物理对象 |
| **智能指针** | 需要自动管理的对象 | 游戏实体、UI 组件 |

### 3. 性能优化技巧

**技巧 1: 预分配容器大小**

### 4. 常见陷阱

**陷阱 1: malloc/free 与 new/delete 混用**
```cpp
// 错误！
int* ptr = (int*)malloc(sizeof(int));
delete ptr;  // 未定义行为

// 正确
int* ptr = (int*)malloc(sizeof(int));
free(ptr);
```

**陷阱 2: 忘记使用 delete[]**
```cpp
// 错误！只调用一次析构函数
FMyObject* arr = new FMyObject[10];
delete arr;  // 内存泄漏

// 正确：调用 10 次析构函数
FMyObject* arr = new FMyObject[10];
delete[] arr;
```

**陷阱 3: TFixedAllocator 超出容量**
```cpp
// 错误！会触发断言崩溃
TArray<int32, TFixedAllocator<3>> Numbers;
Numbers.Add(1);
Numbers.Add(2);
Numbers.Add(3);
Numbers.Add(4);  // 崩溃！超出固定容量

// 正确：使用 TInlineAllocator 允许溢出到堆
TArray<int32, TInlineAllocator<3>> Numbers;
Numbers.Add(1);
Numbers.Add(2);
Numbers.Add(3);
Numbers.Add(4);  // 自动转到堆分配
```

### 6. 总结

**UE5 内存管理哲学**:
1. **性能优先** - 在热点路径使用栈分配和内存池
2. **安全第二** - 使用智能指针管理对象生命周期
3. **灵活性** - 提供多种分配器适应不同场景
4. **可追踪** - 所有分配通过 FMemory 统一管理，便于追踪和调试

**选择指南**:
- **已知小集合** → `TFixedAllocator`
- **通常小集合** → `TInlineAllocator`
- **动态大集合** → `FHeapAllocator`
- **对象管理** → `TUniquePtr` / `TSharedPtr`
- **性能关键** → `FMemory::Malloc` + 手动构造/析构
