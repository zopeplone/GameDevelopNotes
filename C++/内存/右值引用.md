### 万能引用

**核心机制：类型推导 + 引用折叠**

类型推导：模板实参推导对这种形参 `T&&` 有一条特殊规则：
- 若实参是左值：推导 T 为 U&
- 若实参是右值：推导 T 为 U（非引用）


比如下列代码
我们调用 `int a; f(a);` 这里a是lvalue，会推导出 T = int&，于是参数类型变成 int& &&，按“引用折叠”规则折叠为 int&
假如调用 `f(10);` 10是prvalue，会推导出 T = int，于是参数类型是 int&&
```cpp
template<class T>
void f(T&& x); // 这里的 T&& 是万能/转发引用
```

> 为什么不会推导成 T = int&&？***(这里感觉解释不通顺)***
> 因为 T 是模板参数本体，推导时会先确定 T，再把它代回原型形成最终参数类型。对右值实参，规则就是“T 推成非引用类型 U”，这样才能让 T&& 最终得到 U&&。
> 相反，对左值实参如果也推成 U，那 T&& 会变成 U&&，就会让左值也绑定到右值引用，破坏“必须显式 std::move 才能把左值当右值用”的语义。因此标准规定：左值实参时把 T 推成 U&，再通过引用折叠把 U& && 折叠为 U&，从而保留左值属性。


引用折叠：
```cpp
•	&  &  -> &  // 两个左值合并为左值
•	&  && -> &  // 一个左值一个右值合并为左值
•	&& &  -> &  // 一个左值一个右值合并为左值
•	&& && -> && // 两个右值合并为右值
```
即为 ***有左即左，全右才右***

- 什么时候 T&& 不是万能引用?
1.  不是推导出来的 T
```cpp
template<class T>
struct S {
    void g(T&&); // 这里通常不是万能引用：T 在类模板实例化时就固定了，不在 g() 调用点推导
};
```
2. 发生了“别的形式”，不再是裸 T&&
```cpp
template<class T>
void h(std::vector<T>&&); // 不是万能引用，这是纯右值引用
```
3. 明确写死类型
```cpp
void k(int&&); // 纯右值引用
```


## 重要概念

1. 返回右值引用&& 的函数，值类别为`xvalue`
2. `std::move`除了返回右值引用外，不会做其它任何事情（这也就是为什么v还能继续被打印的原因）
3. `xvalue` 本质上还是左值，只是被贴上了”语义“标签的左值，对于一个对象来说，绑定到其身上的左值还是右值都没有区别，都是对a的一个别名
```cpp
int a = 10;
int ra = &a;
int rra = &&a;
cout << a <<endl; // 10
ra = 11;
cout << a <<endl; // 11
rra = 12;
cout << a <<endl; // 12
```
4.  右值引用可以是绑定到`xvalue`,或`prvalue`的引用；左值引用是必须绑定到`lvalue`的引用

## `std::vector` 中的右值

```cpp
MyVector(const MyVector& rhs){
	begin = alloc.allocate(rhs.capacity);
	end = uninitialized_copy(rhs.begin,rhs.end);
	cap = begin+ rhs.capacity;
}


MyVector (MyVector&& rhs) noexcept{
	begin = rhs.begin;
	end = rhs.end;
	cap = rhs.capacity;
	rhs.begin = rhs.end = rhs.capacity = nullptr;
}

```

在拷贝构造函数和移动构造函数中，移动构造函数传入一个右值引用，在函数中将`begin`指针和`end`指针赋给了自身的`begin`和`end`，也就是说在`vector`这种容器中，移动构造函数就是将**传入的资源的持有权转移给了自身**，这就是**移动操作**

- 所以说，绑定到资源上的左值和右值，其实没有本质的区别，他们都是对这个对象的引用，只是在构造函数中对这两种语义进行区分
分为拷贝构造（传入左值引用）和移动构造（传入右值引用）

>构造函数的调用者-> 通过`std::move(a)` 进行承诺：a的资源我不要了，你可以随意移动
>构造函数的实现者->看到参数是右值引用->放心的把资源移动走

引用的左值和右值标签可以理解为构造函数调用者和实现者的一种协议

## 利用右值引用进行开发
### 移动构造函数的实现法则

1. 拷贝其中所有基础数据类型的值;
2. 将其中所有动态内存管理的资源的指针，接管过来;
3. 其中所有自定义类型T，递归地调用T的移动构造函数。
### 保证移后源可析构

- 移后源：指的就是被移动的对象
- 什么叫可析构？
```cpp
MyVector (MyVector&& rhs) noexcept{
	begin = rhs.begin;
	end = rhs.end;
	cap = rhs.capacity;
```

## 完美转发

完美转发是指在函数模板中，能够将参数**原封不动**地传递给另一个函数，保持参数的所有属性：

- 左值还是右值
- const属性
- volatile属性

### 核心问题

在没有完美转发之前，我们遇到这样的问题：

```cpp
void f(const string& s){
	cout<<"左值:"<<s<<endl;
}
void f(string&& s){
	cout<<"右值:"<<s<<endl;
}
void g(const string& s){
	f(s);
}
void g(string&& s){
	f(s);
}
int main(void){
	g(string("Hello1"));
	string s1("hello2");
	g(s1);
}
/*
结果:
左值: Hello1
左值: hello2
*/
```
在g函数中，不管s是左值还是右值，调用f函数时，其参数都为左值（因为s始终是具名变量，不管s是string& 还是 string&&）

所以，如果要真正保留s的值类别，并转发到f函数中，就需要完美转发
```cpp
template<typename T>  
void g(T&& s){  
	f(std::forward<T>(s));  
}
```

### 完美转发的原理

```cpp
template<typename T>
T&& forward(remove_reference_t<T>& arg) {
    return static_cast<T&&>(arg);
}
template<typename T>
T&& forward(remove_reference_t<T>&& arg) {
    return static_cast<T&&>(arg);
}
```
`remove_reference_t` 是去掉T中的所有引用，包括&和&&
这样在参数传递的时候，就可以区分两种函数重载了，并不在arg这里搞万能引用

当T是string&& 时，去掉&&之后，找到第二个重载， arg的类型是string&&，T的类型也是string&&
经过static_cast之后 两个&&合并为一个&&，返回string&&

当T是string& 时，去掉&之后，找到第一个重载， arg的类型是string&，T的类型也是string&
经过static_cast之后 &和&&合并为一个&，返回string&
## `noexcept`
我们发现在MyVector中的移动构造函数中有noexcept关键字
为什么要在移动构造函数中用`noexcept` 关键字声明？

### 定义
`noexcept`是一个修饰符，用于修饰一个函数，用法:
```cpp
void func() noexcept {

}
```
如果一个异常从`noexcept` 函数中逃逸，则程序会立即调用`std::ternimate()` 终止程序
实际使用中，往往是我们100%确定一个函数不会抛出异常，就将其声明为`noexcept`

## 为什么在移动构造函数中，需要使用`noexcept` 来定义呢？

### 1. 保证不产生脏数据

标准库容器（如`std::vector`）在扩容时需要移动或复制元素。如果移动构造函数可能抛出异常，容器会选择使用复制构造函数来保证强异常安全，因为移动构造函数会对移后源进行破坏；移动操作通常只是指针/资源的转移，**本身不应该失败**，如果在这之间发生异常，退回时，移后源可能会是**脏数据**，比如只移动了一部分等等；

```cpp
class MyClass {
public:
    MyClass(MyClass&& other) noexcept {  // 标记为noexcept
        // 移动操作
    }
};

std::vector<MyClass> vec;
vec.push_back(MyClass());  // vector扩容时会使用移动构造
```

如果移动构造函数没有`noexcept`，`std::vector`会退回到复制构造函数（如果可用），导致性能下降。
如果在MyClass的`noexcept` 移动构造函数中，真抛出异常了，则程序直接崩溃，确保没有脏数据的产生
### 2. std::move_if_noexcept的行为

标准库提供了`std::move_if_noexcept`，它会检查移动构造函数是否为`noexcept`：

```cpp
// 有noexcept：返回右值引用，使用移动
// 无noexcept：返回左值引用，使用复制
auto result = std::move_if_noexcept(obj);
```
### 3. 性能优化
1. 减小二进制文件体积
2. 编译器激进优化
3. 与swap函数联动
### 4. C++核心指南明确建议
1. 移动构造函数和移动赋值运算符应当是`noexcept`。
2. 析构函数应当是noexcept(默认就是，但显式标出也没错)0
3. swap函数应当是noexcept。

### 3. MoveTemp() - UE的移动工具

**文件**: `E:\Epic Games\UE_5.4\Engine\Source\Runtime\Core\Public\Templates\UnrealTemplate.h:525-535`

```cpp
/**
 * MoveTemp会将引用转换为右值引用。
 * 这是UE版本的std::move，但当传入右值或const对象时不会编译通过，
 * 因为我们希望在MoveTemp无效时得到通知。
 */
template <typename T>
UE_INTRINSIC_CAST FORCEINLINE std::remove_reference_t<T>&& MoveTemp(T&& Obj)
{
    using CastType = std::remove_reference_t<T>;

    // 验证我们没有传入右值或const对象
    // 前者是冗余的，后者几乎肯定是错误
    static_assert(std::is_lvalue_reference_v<T>, "MoveTemp called on an rvalue");
    static_assert(!std::is_same_v<CastType&, const CastType&>, "MoveTemp called on a const object");

    return (CastType&&)Obj;
}
```

**与 `std::move` 的对比**：
- `std::move` 可以接受任何参数，包括右值和const对象（虽然没有实际效果）
- `MoveTemp` 通过编译期断言拒绝这些情况，**更严格、更安全**
- 这体现了UE对代码质量的高要求：宁可编译失败，也不要隐藏潜在错误

回顾前面的 `std::move` 实现：
```cpp
template <class T>
constexpr remove_reference_t<T>&& move(T&& Arg) noexcept {
    return static_cast<remove_reference_t<T>&&>(Arg);
}
```
可以看到 `std::move` 没有任何检查，而 `MoveTemp` 增加了两个 `static_assert`。

- 这种设计允许类似 `TUniquePtr<Base> = MoveTemp(TUniquePtr<Derived>)` 的操作

### UE实践总结

#### 与标准库的差异
1. **MoveTemp vs std::move**
   - `MoveTemp` 更严格，拒绝右值和const对象
   - 编译期检查，避免无效的移动操作

2. **Forward vs std::forward**
   - 功能相同，都用于完美转发
   - UE版本使用 `UE_INTRINSIC_CAST` 宏标记

#### 常见模式
1. **移动构造/赋值的标准流程**：
   - 转移资源指针
   - 将源对象指针置空（保证移后源可析构）
   - 使用 `MoveTemp` 移动成员

2. **完美转发的三件套**：
   - 模板参数 `T&&`（万能引用）
   - `Forward<T>` 保持值类别
   - `UE_REQUIRES` 或SFINAE约束类型

3. **类型安全**：
   - 大量使用编译期检查（`static_assert`, `UE_REQUIRES`）
   - 删除危险的重载（`= delete`）
   - SFINAE确保类型转换合法
