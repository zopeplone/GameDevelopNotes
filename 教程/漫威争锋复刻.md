# 《漫威争锋》技能与 GAS 战斗框架复刻设计

> 本文目标不是逐字节还原《漫威争锋》商业项目源码，而是把讲座公开的架构、FModel 导出的资源结构，以及 UE 5.8 的 Gameplay Ability System（GAS）源码对齐，形成一套可以在 UE 中落地的复刻方案。
>
> 结论标记：**【讲座】**表示讲座明确提到；**【解包】**表示导出 JSON 可以直接观察到；**【UE 5.8】**表示引擎源码提供的能力；**【复刻建议】**表示根据前三者给出的工程方案，不代表原项目内部实现逐行如此。

## 0. 先说结论

《漫威争锋》的技能系统不是“每个技能一个巨型 GameplayAbility 蓝图”，而是四层组合：

1. **GAS 内核层**：ASC、GameplayAbility、AbilityTask、GameplayEffect、GameplayCue、Attribute、GameplayTag 和预测键，负责授权、状态、数值、网络与生命周期。
2. **数据资产层**：技能条目、技能专用配置、Timeline、BuffSpec、EffectTemplate、投射物/范围检测/召唤物表、输入与 UI 数据，负责描述“这个技能是什么”。
3. **战斗基建层**：检测、生成、战斗数据三条管线，以及 Projectile、Scope/Field、Summoned 三类实体，负责描述“战场规则如何统一执行”。
4. **英雄机制层**：传送门、吸收、反弹、变身、爬墙等不能仅靠通用参数表达的机制，由 C++/蓝图类和自定义 AbilityTask 实现；配置只提供半径、持续时间、引用资产、规则标签等参数。

因此，正确的复刻原则是：

- **代码定义能力边界与算法，配置选择算法并提供参数。**
- **GameplayAbility 负责编排，不直接承包检测、伤害、位移、表现和同步。**
- **伤害结果必须由服务器裁定，客户端预测输入反馈、技能激活、消耗和可回滚位移。**
- **所有战斗数据从统一仓库/管线读取，业务代码不要直接到处查 DataTable。**
- **原生 GAS 是内核，不是完整的英雄射击战斗框架。**Timeline、BuffSpec、TypedCue、实体和三条管线都属于业务扩展。

## 1. 证据范围与解包数据应如何解读

### 1.1 本文使用的材料

- 讲座笔记：`教程/漫威争锋.md`。
- 解包根目录：`Marvel/Content/Marvel/AbilitySystem`，共观察到约 7,811 个 JSON；英雄以 `1011`、`1014` 等 ID 分目录。
- 公共数据目录：`Marvel/Content/Marvel/Data`，共观察到约 3,649 个 JSON；其中 `DataTable` 约 1,309 个文件。
- UE 源码：`Engine/Plugins/Runtime/GameplayAbilities/Source/GameplayAbilities`。

解包中几个很有代表性的数量：

| 资源模式 | 观察数量 | 含义 |
|---|---:|---|
| 数字命名的技能资产，如 `101431.json` | 约 1,116 | 技能条目及其内联专用配置 |
| `Ability_*_BP.json` | 约 1,147 | GameplayAbility 派生蓝图的导出默认值 |
| `Timeline*.json` | 约 1,228 | 自定义 `AnimTimeline` 技能逻辑时间轴 |
| `*BuffSpecTable.json` | 约 157 | 公共、英雄、玩法级 Buff 实例表 |
| `*ScopeAgentTable.json` | 约 139 | 射线、形状、范围与持续检测配置 |
| `*ProjectileAgentTable.json` | 约 109 | 投射物规则配置 |
| `*SummonerAgentTable.json` | 约 93 | 召唤物规则配置 |

这些数量只能描述当前导出快照，不能作为稳定的游戏版本常量。

### 1.2 FModel 能证明什么，不能证明什么

FModel JSON 很适合确认：

- 资源类型、类名、默认属性和对象引用；
- DataTable/CompositeDataTable 的行结构与字段；
- Blueprint CDO 上保存的 Tag、网络策略、可取消性等默认值；
- Timeline 中导出的 Notify 类型、时间轴引用和参数；
- 通用表与英雄子表的组合关系。

但它通常不能完整还原：

- 原项目 C++ 函数体和内部算法；
- Blueprint EventGraph 的所有执行语义；
- 运行时动态生成、热更或服务器下发的数据；
- 同名字段在每一版本中的精确业务含义；
- 讲座里的概念名与资源类名是否一一同名。

所以本文会说“解包显示该技能引用某类配置”，不会把无法看到的函数体写成“原项目就是这样实现”。

## 2. 从一名英雄到一次命中的完整数据链

可以把当前解包呈现的主链理解为：

```text
MarvelHeroTable(HeroId)
  -> MarvelHeroBaseAttributeTable(基础 Attribute、弹药等)
  -> MarvelAbilityTable(CompositeDataTable)
       -> Hero_AbilityTable(AbilityID、输入、CD、AbilityAsset)
            -> MarvelAbilityItem(授予的 GA、Timeline、输入、消耗阶段、专用配置)
                 -> Ability_xxx_BP(Ability/Tag/网络与取消关系)
                 -> AnimTimeline(逻辑节点 + Montage)
                 -> ExtendConfigInline(技能独有参数)
                 -> Scope / Projectile / Summoner / BuffSpec 引用
                      -> EffectTemplate / GameplayEffect
                      -> GameplayCue / TypedCue / Niagara
```

实际命中流程则是：

```text
Enhanced Input
  -> ASC 尝试激活 Ability
  -> CanActivate + Tag/Cost/CD 检查
  -> Ability 启动一个或多个 AbilityTask
  -> Task 播放 AnimTimeline、等待输入或请求生成战斗实体
  -> Timeline Notify 触发 Scope/Projectile/Summoner/Buff/Cue
  -> 检测管线筛选目标
  -> 服务器构造伤害/治疗 GameplayEffectSpec
  -> ASC 应用 Effect，修改 Attribute/Tag/Buff 状态
  -> GameplayCue/TypedCue 播放表现
  -> EndAbility 清理 Task、标签、镜头和预测对象
```

### 2.1 真实样本：惩罚者主武器

`1014_AbilityTable` 中 `101431` 是“审判者”，绑定 `MouseLeft`。其技能资产 `101431.json` 包含：

- `MarvelAbilityItem`：授予 `Ability_101431_BP_C`；绑定 `IA_PrimaryAttack`；激活模式为 Click。
- `Config_105`：`EquipID=101401`、`FireModeIndexes=[0,1]`、`bRoundRobin=true`、松开后延迟结束 `0.2` 秒，并引用后坐力/冲量曲线。
- 英雄目录还有 `1014_InstantAmmoTable`、`ProjectileAgentTable`、`ScopeAgentTable` 与 Equipment 表。

这说明“枪线模板”不是一个表字段完成全部功能，而是 Ability 编排 + 武器/射击模式 + 瞬时弹药/投射物 + 检测表 + 曲线的组合。

### 2.2 真实样本：奇异博士传送门

`1018_AbilityTable` 中 `101861` 是“法瑞拉五星阵”。`101861.json` 的专用 `Config_101861` 可观察到：

- 放置相机偏移、初次放置偏移；
- 相机插值时间和多档移动速度；
- `TracePortalRadius=250`；
- 阻挡 Collision Channel 与 Pawn Trace Channel；
- 放置预览 Actor 与相机 Actor 类；
- 穿透检查、要求的组件 Tag、盒体尺寸；
- `AbilityDuration=500`；
- 技能条目引用 Start/Open 两条 Timeline，并绑定放置输入方法。

此外 `ScopeAgentTable` 中普遍存在 `bCanCrossPortal`、`bPortalAsTraceResult` 等字段。它证明传送门并非只是一段英雄 Ability：检测框架本身预留了“射线能否过门、门是否算命中结果”的全局能力。角色、相机、弹道和渲染穿越的矩阵算法仍必须由代码实现。

### 2.3 真实样本：万磁王吸收

`103751`“钢铁汲取”的 `PyConfig_103751` 可观察到：

- `AbsorbType`；
- 不同吸收对象对应的资源恢复映射；
- 吸收检查时长、吸收持续时间与检测频率；
- 检测体大小、起点、选择 Task 参数；
- 冷却相关 Tag。

这些字段能配置“吸收什么、多久扫一次、范围多大、回多少资源”，但“如何接管在途投射物、怎样终止或改写其生命周期、如何处理瞬时弹道”是管线算法，必须写代码。

### 2.4 真实样本：美国队长盾牌

`1022_AbilityTable` 中 `102241` 为“绝对意志”。其专用配置可见反射方向、扩散上下限、额外伤害检测形状、伤害衰减比例和 Buff 列表等字段。英雄的 Scope/Projectile 表同时描述具体检测和投射物。

配置能表达反射参数；真正的反射流程仍要由代码完成：截获检测段或投射物命中，计算新方向，更新 Source/Instigator/Team，重建后续 Trace，防止无限反弹，并维护伤害归因。

## 3. GAS 内核如何分工

### 3.1 Ability System Component（ASC）

ASC 是每个战斗参与者的能力与状态容器，负责：

- 保存 `FGameplayAbilitySpec` 并授予、移除、激活技能；
- 保存 Active Gameplay Effects、聚合 Attribute 修改；
- 维护 Owned Gameplay Tags；
- 复制 Ability、Effect、Cue、Tag 和预测键；
- 连接 OwnerActor 与 AvatarActor。

UE 5.8 源码入口：

- `AbilitySystemComponent.h`：`GiveAbility`、`TryActivateAbility`、`InitAbilityActorInfo`、`ApplyGameplayEffectSpecToSelf/Target`。
- `AbilitySystemComponent_Abilities.cpp`：`InternalTryActivateAbility`、`InternalServerTryActivateAbility`。

**复刻建议**：玩家角色把 ASC 放在 `PlayerState` 上，使死亡换 Pawn 后长期 Buff/CD 仍可保留；召唤物若需要技能、Buff 和属性，则自身持有精简 ASC。Avatar 变化后必须在服务器和拥有客户端重新调用 `InitAbilityActorInfo`。

### 3.2 GameplayAbility

Ability 负责一次技能的授权和流程编排：

- 能否激活；
- 何时提交 Cost/CD；
- 获得/阻挡/取消哪些 Tag 或 Ability；
- 启动哪些异步 Task；
- 何时成功、取消或结束。

解包 `Ability_*_BP` 的 CDO 能观察到大量原生/扩展字段：

- `AbilityTags`；
- `ActivationOwnedTags`、`ActivationRequiredTags`、`ActivationBlockedTags`；
- `CancelAbilitiesWithTag`、`BlockAbilitiesWithTag`；
- `bIsCancelable`、循环技能标志；
- `NetExecutionPolicy`、`ReplicationPolicy`；
- 项目扩展的 `ConsistentCancelConfig` 等。

不要在 `ActivateAbility` 中写一个几百节点的大图。推荐让 Ability 只做：读取 `FAbilityDefinition`、创建上下文、按配置启动模板 Task、监听完成/取消并调用 `EndAbility`。

### 3.3 AbilityTask

AbilityTask 是技能里的异步行为单元。UE 5.8 的 `UAbilityTask` 继承 `UGameplayTask`，标准扩展点是工厂函数、`Activate()`、Delegate 和 `OnDestroy()`。

建议建立这些项目级 Task：

| Task | 职责 |
|---|---|
| `UAT_PlayCombatTimeline` | 播放逻辑 Timeline 与 Montage，转发节点事件 |
| `UAT_WaitEnhancedInput` | 处理按下、松开、长按、蓄力与二段输入 |
| `UAT_RunHitscan` | 调用检测管线执行一次或循环枪线 |
| `UAT_SpawnProjectile` | 经生成/实体服务创建预测或权威投射物 |
| `UAT_RunScope` | 扇形、球、盒、胶囊、射线或持续范围检测 |
| `UAT_SpawnSummoned` | 创建召唤物并等待死亡/数量规则 |
| `UAT_ApplyConfiguredBuff` | 根据 BuffSpec 构造并应用 GE Spec |
| `UAT_AbilityDash` | 可预测位移、碰撞、取消与服务器校正 |
| `UAT_WaitGameplayTagQuery` | 等待状态条件进入/退出 |

所有 Task 必须在 `OnDestroy` 解除 Delegate、停止计时器、归还实体句柄并调用 `Super::OnDestroy`。异步回调前检查 Ability 是否仍有效，避免技能结束后继续造成伤害。

### 3.4 GameplayEffect、AttributeSet 与 Buff

原生 GameplayEffect（GE）适合表达：

- Instant / HasDuration / Infinite；
- Attribute Modifier（Add/Multiply/Override 等）；
- 周期执行；
- GameplayTag 授予、需求、免疫；
- Stacking 与溢出；
- GameplayCue；
- Granted Abilities；
- Execution Calculation。

UE 5.8 的 `GameplayEffect.h` 中可以直接找到 `DurationPolicy`、`Modifiers`、`Executions`、`GameplayCues`、`StackLimitCount` 等定义。

要特别注意 UE 5.8 与许多旧 GAS 教程的差异：授予 Ability、目标 Tag、应用需求、免疫、阻挡/取消技能、移除其他 Effect、追加 Effect 等组合行为已经由 `UGameplayEffectComponent` 体系承载。旧的 `UGameplayEffect::GrantedAbilities` 在源码中已标记为废弃，应分别使用 `UAbilitiesGameplayEffectComponent`、`UTargetTagsGameplayEffectComponent`、`UTargetTagRequirementsGameplayEffectComponent`、`UImmunityGameplayEffectComponent`、`UBlockAbilityTagsGameplayEffectComponent`、`UCancelAbilityTagsGameplayEffectComponent` 等组件。复刻 Buff 模板时应生成/配置这些现代组件，而不是继续依赖旧字段。

推荐至少拆出：

- `UHeroVitalSet`：Health、MaxHealth、Shield、Energy；
- `UHeroCombatSet`：AttackPower、Defense、MoveSpeed、Crit 等；
- `UHeroAmmoSet`：当前弹药、最大弹药、特殊资源；
- Meta Attribute：IncomingDamage、IncomingHealing，用 Execution 结算后归零。

伤害公式、护盾吸收、暴击、队伍规则、击杀归因等应放在 `UGameplayEffectExecutionCalculation` 与服务器战斗结算服务中，不要散落在每个英雄 Ability。

### 3.5 GameplayCue

GameplayCue 只负责表现，不应成为伤害权威逻辑。原生 Cue 支持 Execute、OnActive、WhileActive、Removed；Ability 也能直接 Execute/Add/Remove Cue。

讲座中的 TypedCue 是 GAS Cue 与 Niagara/SkeletalMesh/Audio 之间的项目中间层。复刻时可以做：

```text
GameplayCue Tag
  -> UTypedCueDefinition(DataAsset)
       -> 生成策略：一次性 / 持续 / 附着 / 世界空间
       -> Niagara、音效、材质、镜头震动
       -> 参数绑定表：Magnitude、位置、命中法线、骨骼、阵营、颜色
  -> UTypedCueComponent / Pool
```

Niagara 反向读取战斗数据时，写自定义 `UNiagaraDataInterface`，只暴露稳定的只读快照，如 Health Ratio、Shield Ratio、Team、状态位。不要让 Niagara 修改 ASC 或直接触发伤害。

## 4. 技能“三态配置”在解包中的实际对应

讲座把技能拆为 AbilitySet、AbilityConfig、AbilityPriority。解包里不一定存在三个同名文件，但职责可以清楚映射。

### 4.1 AbilitySet：通用技能条目

解包中最接近 AbilitySet 的是数字命名资产里的 `MarvelAbilityItem`，再加英雄 `AbilityTable` 的索引行。它们可配置：

- AbilityID、名称、描述、启用状态；
- Ability 类资产；
- 输入键位、InputAction、Click/Hold/Release 等激活方式；
- Timeline 列表和动画资源索引；
- CD、充能次数、共享 CD、死亡后是否保留；
- 资源消耗、准备/提交 Cost 与 CD 的技能阶段；
- UI Tag、反馈、镜头震动、命中反馈；
- GameplayCue 引用；
- 技能统计、战斗日志、伤害类型等外围元数据。

这里的“Set”是业务概念，不应与 UE 自带的 `UAbilitySet` 示例类混淆。

### 4.2 AbilityConfig：每个技能的专用参数

数字技能资产经常同时导出一个 `Config_*`、`PyConfig_*` 或具体技能类配置，并由 `ExtendConfigInline` 引用。全量样本中能看到：

- 通用飞行、二段跳、高跳、长按触发等配置类；
- 武器 EquipID、FireModeIndexes；
- Dash 参数、速度、重力、转向、胶囊体；
- ScopeID、ProjectileID、SummonerID、BuffID；
- 吸收半径、传送门碰撞、相机速度等英雄独有字段。

这是一种“多态配置”：共同框架读取基类接口，具体模板再 Cast 到自己的 UScriptStruct/UDataAsset 类型。不要把所有英雄字段塞进一个 500 列总表。

### 4.3 AbilityPriority：关系配置

解包中的关系数据主要以以下形式出现：

- Ability 蓝图上的 `CancelAbilitiesWithTag`、`BlockAbilitiesWithTag`；
- `ActivationRequired/BlockedTags`；
- Timeline 的 `AnimNotifyState_TimedBlockTags`，临时设置阻挡/取消关系；
- `ConsistentCancelConfig`；
- `AbilityActivateData_Base.ActivatePriorityType`，可见 BoundAbility、SelectAbility、LevelInteractiveAbility、CustomPriority 等枚举值；
- CD ID、共享 CD、技能阶段提交等关系。

**复刻建议**：用 GameplayTag 表达“类别关系”，用显式优先级解决同帧竞争：

```cpp
USTRUCT(BlueprintType)
struct FAbilityRelationRule
{
    FGameplayTagQuery SourceQuery;
    FGameplayTagQuery TargetQuery;
    int32 Priority = 0;
    EAbilityRelationAction Action; // Block, Cancel, Queue, Replace
};
```

规则合并顺序必须固定，例如：玩法覆盖 > 英雄覆盖 > 技能显式规则 > 类别默认规则。冲突时输出包含来源资产的调试记录。

## 5. AnimTimeline：技能逻辑时间轴

### 5.1 它不是什么

它不是 Actor 上的 `UTimelineComponent`，也不只是 Animation Montage Notify 的别名。解包显示 Timeline 主对象类型是自定义 `AnimTimeline`，典型字段有：

- `AnimNotifyTracks`；
- `AnimSections`；
- `SequenceLength`；
- `MontagePath`；
- 部分资产还有快速 Tick、自动停止等选项。

它把逻辑轨道与 Montage 资源关联，使“逻辑时间”和“骨骼动画”能协作又可分离。

### 5.2 解包中真实存在的节点类型

在约 1,228 条 Timeline 中，常见导出节点包括：

| 节点 | 观察到的用途 |
|---|---|
| `MarvelTagNotify_Missile/Break/Pick/Begin/End` | 技能阶段与事件 Tag |
| `AnimNotify_SpawnScope` | 按 ScopeID 生成范围/射线检测 |
| `AnimNotify_SpawnProjectile` | 按 ProjectileID 发射投射物 |
| `AnimNotify_SpawnSummoner` | 按 SummonerID 创建召唤物 |
| `AnimNotify_ApplyBuff/RemoveBuff` | 加/移除 Buff，可覆写时长和数值 |
| `AnimNotifyState_TimedOwnedTags` | 在区间内授予状态 Tag |
| `AnimNotifyState_TimedBlockTags` | 在区间内阻挡/取消 Ability Tag |
| CameraShake / CameraInterp | 镜头反馈 |
| WeaponEvent | 武器事件与换弹阶段 |
| `MarvelTagNotify_EndAbility` | 显式结束 Ability |

### 5.3 UE 中的实现方式

建议定义 `UCombatTimelineAsset`，内部保存稳定 ID、长度、Montage 软引用、Section 和按时间排序的 `FCombatTimelineEvent`。事件 Payload 使用实例化结构体：

```cpp
USTRUCT(BlueprintType)
struct FCombatTimelineEvent
{
    float StartTime = 0.f;
    float EndTime = 0.f;
    FGameplayTag EventTag;
    UPROPERTY(EditAnywhere, meta=(BaseStruct="/Script/YourGame.CombatTimelinePayload"))
    FInstancedStruct Payload;
};
```

运行器必须支持：

- 从指定 Section/归一化时间开始；
- 播放速率变化后保持逻辑时间一致；
- Begin/Tick/End 区间事件；
- 技能取消时逆序清理仍处于激活状态的区间节点；
- 服务器与拥有客户端独立推进，关键事件用预测键去重；
- Dedicated Server 不加载纯视觉资产，但仍执行权威逻辑节点；
- 编辑器预览、断点、逐帧、命中体可视化和配置校验。

逻辑命中时刻不要只依赖 Montage Notify 的网络复制；服务器必须按自己的 Timeline 时间执行权威节点。

## 6. Buff 三层架构

讲座的三层是 Effect → Buff → CDR（Condition/Disable/Restrict）。可以这样落地。

### 6.1 EffectTemplate：共性效果模板

`MarvelEffectTemplate` 的导出行直接包含：

- EffectTag、效果类型 Tag、描述；
- DurationPolicy、AttributeTag、ModifierOp；
- 优先级；
- Block、Dispel、BeDispelled、Inhibited、Require 状态；
- 叠层规则、溢出、共存、周期、层数上限；
- 死亡自动移除、死亡时能否应用；
- Animation/FX/UI/ScreenFX 等 Cue 通道；
- AssetTags、GrantTags；
- 授予 Ability；
- 韧性保护等项目扩展。

它负责定义“眩晕类/数值减益类效果通常怎样工作”。

### 6.2 BuffSpec：技能上的具体实例

英雄 `BuffSpecTable` 的行字段包含：

- EffectID、AttributeValue、Duration、Period；
- 数值扩散/曲线/百分比伤害或治疗；
- 是否覆盖模板的持续、叠层、Cue、生命周期；
- Source 间叠层限制、刷新/替换/累加时长；
- 预测生成/预测删除、同步半径；
- Granted Abilities、Grant/Block/Cancel Tags；
- Begin/End/Break/Custom Buff 链；
- GameplayCues、日志与地形死亡相关配置。

这层表达“某英雄的某个技能施加一个 3 秒、数值为 20、最多叠 2 层的减速”。

### 6.3 CDR：最小行为限制

CDR 不应再生成大量 GE 类。用稳定 Tag 与组件响应器表达：

- `State.Disable.Move`：CharacterMovement 拒绝移动输入；
- `State.Disable.Jump`：跳跃 Ability 的 ActivationBlockedTags；
- `State.Restrict.Targetable`：检测管线的 Target 过滤；
- `State.Condition.Invulnerable`：伤害 Execution/规则管线检查；
- `State.Disable.Ability.Primary`：Ability Tag 阻挡。

GE/Buff 只负责授予/撤销这些 Tag；实际系统订阅 Tag 变化并执行行为。这样不会让每个 Buff 各写一遍“不能移动”。

### 6.4 推荐的应用流程

```text
技能请求 BuffSpecID
  -> BuffRepository 合并 EffectTemplate + BuffSpec + 玩法覆盖
  -> 校验 Require / Block / Dispel / Immunity
  -> 构造 FGameplayEffectSpec
  -> SetByCaller 写入数值、持续时间、来源技能、命中信息
  -> 服务器 ASC ApplyGameplayEffectSpecToTarget
  -> GE 授予 Attribute/Tag/Ability
  -> CDR 响应器改变行为
  -> Cue 表现
```

不要运行时为每个 Buff 动态创建新的 UGameplayEffect 类。准备少量模板 GE/Component，用 Spec、SetByCaller 与项目数据解释器填参数。

## 7. 三类战斗实体与三条管线

### 7.1 Projectile：延迟弹道

`ProjectileAgentTable` 的字段范围很大，能配置：

- Actor 类、碰撞规则、Tag/Buff 需求；
- 弹跳、摩擦、弹性、次数；
- 穿透次数、穿透后距离、伤害衰减曲线；
- 瞄准方向、基础伤害、冲量、Buff、Cue；
- 客户端结果、服务器校验、位置修正、批量 RPC；
- 快速/虚拟投射物、并行更新、不可见更新频率；
- 缓存、相关性与复制优化。

**代码负责**运动积分、Sweep、命中去重、网络校验、回滚/补偿、对象池与反弹/传送重建；**配置负责**选用哪种策略及其参数。

### 7.2 Scope/Field：即时与持续检测

讲座称法阵/检测场，资源中主要体现为 `ScopeAgentTable`。可配置项包括：

- Line/Sphere/Capsule/Box/Sector 等 TraceType 与形状；
- Length、Radius、HalfHeight、BoxSize、水平/垂直角；
- 起点 Anchor、Offset、方向与排序；
- 单/多目标、场景遮挡、目标过滤；
- Source/Target Tag 与 Buff Requirements；
- 是否跨传送门、是否把传送门作为结果；
- 客户端相机信息、客户端结果、服务器验证；
- 伤害、冲量、Buff、移除 Buff、Cue；
- 最大应用次数、应用间隔、每次检测 Cost。

### 7.3 Summoned：召唤物

`SummonerAgentTable` 可观察到：

- 是否需要 ASC、AttributeSpec、初始 Buff；
- 对自身/队友/敌人的 Tag Requirements；
- Scope/死亡 Scope/Ability 引用；
- 数量组、上限和唯一 Tag；
- 统计策略、成本控制策略；
- 死亡是否结束 Task；
- Cue、预测 Cue、回滚支持；
- 可见性、AI 感知、网络相关性、缓存。

召唤物不是简单 `SpawnActor`。有独立生命、技能或 Buff 的召唤物应走统一实体管理器，纯视觉临时物则不要创建 ASC。

### 7.4 检测管线

推荐接口：

```text
FDetectionRequest
  SourceContext(Actor/Ability/Team/Tags/PredictionKey)
  Geometry(Line/Sphere/Box/Sector...)
  RuleTags
  TargetRequirements
  PortalPolicy
```

执行顺序：

1. 收集玩法全局规则（队伤、目标类别、活动修改）。
2. 合并 Source 的检测类型、阵营、状态和忽略列表。
3. 用粗筛 Collision Channel/Spatial Query 得到候选。
4. 收集 Target 的阵营、Tag、Buff 与被检测规则。
5. 应用距离、角度、遮挡、去重、次数和优先级。
6. 经过 Portal/Reflect/Absorb 等拦截器分段或改写。
7. 返回稳定排序、带完整上下文的命中结果。

扩展点应是注册式拦截器：`PreTrace`、`PostCandidate`、`PreHitCommit`、`RewriteSegment`，而不是在所有 Projectile 和 Scope 中写 `if DoctorStrange`。

### 7.5 生成管线

生成英雄时构造一个不可变快照：

```text
Base Hero Definition
  + Skin/Body/CharacterClass
  + Base Attributes
  + Default Ability Set
  + GameMode Mutators
  + Team-up/Bond Abilities
  + Player progression/loadout
  = FResolvedHeroSpawnSpec
```

服务器依据快照 Spawn Pawn、初始化 ASC/Attribute、授予 Ability、应用初始 GE/Buff，再复制必要结果。客户端不得自己决定最终技能集或基础属性。

### 7.6 战斗数据管线与 Effector

所有业务读取都走类型化 API：

```cpp
float GetAbilityCooldown(FAbilityId Id, const FCombatDataContext& Context);
const FResolvedBuffSpec& GetBuff(FBuffId Id, const FCombatDataContext& Context);
const FResolvedScopeSpec& GetScope(FScopeId Id, const FCombatDataContext& Context);
```

解析顺序可以是：基础数据 → 英雄覆盖 → 模式 Effector → 活动/热更 → 运行时临时规则。每一步记录：旧值、新值、修改器 ID、优先级和来源资产。

不要做“通过字符串反射任意改所有 UObject 字段”的万能覆盖器。为允许修改的字段建立类型化 Patch，并在 Cook/CI 时验证范围和冲突。

## 8. 技能模板系统怎么搭

模板是 AbilityTask 之上的固定编排，不是复制一批 Blueprint。

### 8.1 枪线模板

```text
Activate
  -> 校验武器/弹药/状态
  -> 启动 Timeline 和 WaitInput
  -> Missile/Fire 节点
       -> 读取 FireMode + InstantAmmo/Scope
       -> 获取客户端瞄准数据
       -> 服务器重建并验证射线
       -> Detection Pipeline
       -> Damage Execution + Buff + Cue
  -> Recovery/Break
  -> EndAbility
```

配置：射速、散布、连发、射线形状、距离、衰减、伤害、弹药、镜头和 Cue。代码：反作弊校验、命中补偿、散布种子、批量 RPC、伤害裁定。

### 8.2 投射物模板

Timeline 到点调用 `UAT_SpawnProjectile`。配置初速度、重力、碰撞、穿透、弹跳、生命周期、命中 Scope/Buff/Cue；代码负责权威运动、预测替身与服务器对象的匹配、命中重放和特殊管线拦截。

### 8.3 二段跳/飞行/冲刺模板

解包中可见 `MarvelAbilityConfig_DoubleJump`、飞行、高跳、Dash 等配置类型。配置速度、重力、次数、转向、消耗、持续时间和状态 Tag；代码负责 CharacterMovement 自定义 MovementMode、SavedMove/NetworkPrediction、碰撞和服务器校正。

不要只在 Ability 中每 Tick `SetActorLocation`，否则网络移动、斜坡、碰撞和回滚都会失控。

### 8.4 变身模板

变身牵涉 Avatar、Mesh、AnimInstance、Attribute、技能集、碰撞和相机。服务器提交状态切换，生成管线解析新形态，ASC Owner 保持稳定并切 Avatar/技能集。按讲座原则，变身结果不做完全客户端预测；本地可以先播前摇和 Cue，权威确认后再切换实体状态。

### 8.5 唯一技能

传送门、全弹道吸收、盾牌反射等应使用“专用机制类 + 通用管线扩展点 + DataAsset 参数”。独特不等于把一切硬写死：数学与生命周期写代码，数值、Tag、资产引用、过滤规则仍配置化。

## 9. 客户端预测与服务器权威

### 9.1 UE 5.8 原生流程

`GameplayPrediction.h` 对激活预测的描述很清晰：

1. 客户端 `TryActivateAbility`，生成 `FPredictionKey`，本地先执行并 RPC 到服务器。
2. 服务器用同一 Key 进入 `FScopedPredictionWindow`，再次执行 `CanActivateAbility`。
3. 失败则拒绝 Key，客户端执行 Rejected Delegate 并撤销预测副作用。
4. 成功后等待属性复制追上，PredictionKey CaughtUp，用键抑制重复 Cue/Effect 表现。

UE 5.8 原生可预测 GE 的 Attribute Modifier、Tag 与 Cue；源码也明确注明 GameplayEffect Execution 不能按同样方式预测。链式 Ability 的完整回滚也不是开箱即用。

### 9.2 哪些预测，哪些不预测

| 行为 | 建议 | 原因 |
|---|---|---|
| 输入反馈、短前摇、镜头、枪口 FX | 本地立即 | 直接影响手感，权威状态少 |
| Ability 激活、Cost/CD | GAS LocalPredicted | GAS 有 PredictionKey 与 GE 对账 |
| 冲刺/移动 | 预测，但走移动预测 | 需要 SavedMove/服务器校正 |
| 本地投射物替身 | 可预测表现 | 服务器投射物才有权造成最终伤害 |
| 敌方伤害、治疗、硬控 | 服务器 | 难回滚且涉及公平性 |
| 变身/复活/生成英雄 | 服务器确认 | 跨多个复制系统，回滚成本高 |
| AI、环境和非拥有客户端 Ability | ServerInitiated/ServerOnly | 客户端没有合法预测所有权 |

### 9.3 预测对象的工程约束

- 每个预测生成物保存 `PredictionKey + LocalSequence`，服务器实体到达后配对并替换。
- Cue、命中反馈和 Timeline 节点必须用 Key/事件序号去重。
- 被拒绝时停止 Task、移除预测 GE/Tag、清理持续 Cue、归还预测实体并触发移动校正。
- 服务器永远重算关键命中；客户端只提交受限的起点、方向、时间戳和种子。
- 对网络延迟、丢包、乱序和 20 Hz/60 Hz 不同帧率做自动化测试。

解包中的 `bShouldPredictSpawn/Delete`、`bUseClientResult`、`bServerVerifyClientResult`、`bSupportRollback`、批量 RPC、位置修正等字段，正说明预测与网络策略本身也是每类实体的配置维度，但这些布尔值背后的网络协议必须写代码。

## 10. 哪些可以配置，哪些必须写代码

判断标准不是“能不能做成字段”，而是“把它配置化是否形成稳定、可验证、可复用的语义”。

| 模块 | 适合配置 | 必须由代码提供 |
|---|---|---|
| Ability | 类、输入、CD、Cost、阶段、Tag、Timeline、UI | 激活/结束协议、Task 编排器、异常清理 |
| Ability 关系 | Tag Query、优先级、Block/Cancel/Queue | 冲突解析算法、同帧确定性、调试记录 |
| Timeline | 时间、Section、Payload、Montage、节点类型 | 调度、网络去重、取消清理、编辑器 |
| Attribute/伤害 | 基础值、曲线、倍率、伤害类型 | 聚合、护盾/暴击/减伤公式、权威结算 |
| Buff | 模板、时长、周期、层数、驱散、Tag、Cue | Spec 构造、互斥/驱散执行、CDR 响应 |
| Scope | 形状、尺寸、过滤、排序、遮挡、频率 | 空间查询、Portal 分段、反作弊、性能预算 |
| Projectile | Actor、速度、弹跳/穿透、Cue、Buff | 运动与 Sweep、复制、预测匹配、吸收/反弹 |
| Summoned | 类、数量、属性、初始 Buff、技能、相关性 | 生命周期、所有权、ASC 初始化、对象池 |
| Cue | 资产、附着点、参数映射、LOD、持续策略 | TypedCue 执行器、池、复制与去重 |
| 模式 Effector | 允许覆盖的字段和值、条件、优先级 | 合并算法、白名单、缓存、审计与校验 |
| 传送门 | 尺寸、碰撞通道、持续、相机参数 | 空间变换、递归渲染、射线分段、跨门同步 |
| 吸收/反弹 | 范围、对象类型、次数、恢复值、衰减 | 生命周期截获、Source/Team 改写、归因、防循环 |

### 10.1 一个简单的边界测试

满足以下条件的内容优先做配置：

- 是已有算法的参数或策略选择；
- 策划需要频繁调整；
- 可以在加载时静态校验；
- 改动不会改变网络协议和安全边界。

满足以下条件的内容优先写代码：

- 新的空间算法、移动模式或网络协议；
- 涉及服务器权威、反作弊或回滚；
- 需要管理 UObject/Actor 生命周期、异步与资源清理；
- 需要性能关键的数据结构或批处理；
- 配置语言若要表达它，最终会变成难调试的脚本语言。

## 11. 推荐的 UE 工程架构

```text
Source/MarvelReplica/
  AbilitySystem/
    ReplicaAbilitySystemComponent
    ReplicaGameplayAbility
    AttributeSets/
    AbilityTasks/
    Effects/
    Prediction/
  CombatData/
    Definitions/       // Ability, Buff, Scope, Projectile, Summoned
    Repository/        // ID 查询、缓存、版本与校验
    Effectors/         // 模式覆盖
  CombatTimeline/
    Runtime/
    Editor/
  CombatPipeline/
    Detection/
    Spawn/
    Damage/
  CombatEntities/
    Projectile/
    Scope/
    Summoned/
  GameplayCues/
    TypedCue/
    NiagaraDataInterface/
  HeroMechanics/
    Portal/
    Absorb/
    Reflect/
    Transform/
```

建议依赖方向：`HeroMechanics -> Pipeline -> AbilitySystem/CombatData`，底层模块不得反向依赖具体英雄 ID。

### 11.1 核心数据结构

推荐用 Primary Data Asset 做可发现的顶层定义，用 DataTable 管大量同构行，用 `FInstancedStruct` 承载多态扩展：

```cpp
UCLASS(BlueprintType)
class UAbilityDefinition : public UPrimaryDataAsset
{
    GENERATED_BODY()
public:
    FName AbilityId;
    TSoftClassPtr<UGameplayAbility> AbilityClass;
    FGameplayTagContainer AbilityTags;
    TObjectPtr<UCombatTimelineAsset> Timeline;
    FAbilityInputConfig Input;
    FAbilityCostConfig Cost;
    FAbilityCooldownConfig Cooldown;
    FInstancedStruct TemplateConfig;
};
```

生产项目不要依赖裸 `int32` 在模块间传递。至少包装成 `FAbilityId`、`FBuffId`、`FScopeId`，或统一用带命名空间的 PrimaryAssetId，并提供 Cook 校验。

### 11.2 初始化流程

```text
GameInstance 加载公共战斗数据与 Tag
  -> GameMode 注册规则/Effector
  -> PlayerState 创建 ASC
  -> Spawn Pipeline 解析 HeroSpawnSpec
  -> Spawn Pawn
  -> ASC InitAbilityActorInfo(PlayerState, Pawn)
  -> 初始化 Attribute Base 值
  -> 服务器 GiveAbility
  -> 应用初始 Buff/Passive
  -> 客户端 OnRep 后绑定输入与 UI
```

授予 Ability、设置基础 Attribute、应用权威初始 Buff 都在服务器执行。

### 11.3 输入

解包公共 `AbilityInputActionTable` 把 `PrimaryAttack`、`SecondaryAttack`、Ability1-4、Ultimate 等枚举映射到 Enhanced Input 的 `IA_*` 资产；具体 AbilityItem 又能配置 BindInputAction 和激活方式。

复刻时不要把 InputID 直接等同键盘键。使用三层映射：

```text
Physical Key / Gamepad
  -> Enhanced InputAction
  -> Semantic Ability Input Tag
  -> ASC 中满足该 Input Tag 的 AbilitySpec
```

这样换键、手柄、自定义英雄输入与观战输入不会污染 Ability 代码。

## 12. 技能编辑器应做到什么

讲座强调“一站式”。真正有价值的编辑器不是把 Details Panel 拼在一起，而是提供跨资产上下文和校验。

最低可用功能：

1. 左侧技能列表：英雄、AbilityID、输入、CD、模板类型、引用状态。
2. 中央 Timeline：逻辑轨道、Montage 波形/Section、Scope/Projectile/Buff/Cue 节点。
3. 右侧上下文 Details：节点 Payload 与对应表行联动编辑。
4. 预览世界：角色动画、命中体、弹道、Cue、相机。
5. 网络预览：LocalPredicted/ServerOnly、模拟 RTT/丢包、显示 PredictionKey。
6. 数据溯源：当前值来自基础、英雄、模式还是热更 Effector。
7. 静态校验：悬空 ID、非法 Tag、循环 Buff、无结束路径、服务器逻辑引用纯客户端资产。
8. 性能预算：每秒 Trace、最大候选数、投射物/召唤物上限、Cue LOD。

建议先完成运行时和命令行校验器，再做华丽编辑器；否则编辑器会掩盖不稳定的数据契约。

## 13. 分阶段复刻路线

### 阶段一：GAS 垂直切片

- 一个 Hero、ASC、Health/Energy/Ammo AttributeSet；
- Enhanced Input 到 Ability 激活；
- 一次枪线、服务器伤害、Cue；
- CD/Cost 与 LocalPredicted；
- Dedicated Server 双客户端测试。

验收：150 ms RTT 下开火立即有本地反馈，服务器拒绝时 Cost/CD 能对账，伤害只由服务器产生。

### 阶段二：数据化与 Timeline

- AbilityDefinition、BuffSpec、ScopeSpec、ProjectileSpec；
- CombatTimeline 与 5 个核心节点；
- 数据仓库、引用校验和调试溯源；
- 枪线、投射物、Dash 三种模板。

### 阶段三：Buff/CDR 与实体

- EffectTemplate + BuffSpec 合并；
- 移动/跳跃/技能/可选取 CDR；
- Projectile、Scope、Summoned 统一生命周期；
- 对象池、相关性与服务器性能统计。

### 阶段四：三条管线

- Source/Target 双向检测规则；
- SpawnSpec 与玩法变体；
- 类型化 Effector；
- 确定性优先级与完整审计。

### 阶段五：特殊机制

建议顺序：盾牌反射 → 吸收 → 单层传送门检测 → 角色/投射物穿门 → 相机与递归渲染。传送门是跨模块验收题，不适合作为第一项功能。

## 14. 测试与常见坑

### 14.1 必须自动化的测试

- Ability Tag 的 Block/Cancel/Required 组合；
- Buff 叠层、刷新、溢出、驱散、免疫与死亡清理；
- Timeline 在取消、跳 Section、变速、掉帧后的节点顺序；
- 检测结果在客户端/服务器和不同帧率下的稳定排序；
- PredictionKey 成功、拒绝、超时和重复 RPC；
- 投射物穿透/反弹/传送后的伤害归因和 Team；
- Effector 合并优先级、非法字段与版本兼容；
- Dedicated Server 不加载/执行纯表现对象。

### 14.2 高风险误区

- **把 GameplayTag 当布尔变量仓库**：Tag 要有命名规范、所有者和生命周期，临时 Tag 必须成对清理。
- **把所有伤害都做成普通 Modifier**：复杂护盾、暴击、命中部位、模式规则应集中到 Execution/结算管线。
- **相信客户端命中结果**：可以接受客户端候选以改善手感，但服务器必须验证历史姿态、起点、方向、距离和遮挡。
- **只靠 Montage 驱动服务器逻辑**：Montage 播放状态不是可靠的权威战斗时钟。
- **用 Blueprint Tick 管数百弹道**：需要批处理、虚拟弹道或原生 C++ 管理器。
- **万能 DataTable**：异构技能应使用多态配置，不要不断添加仅一个英雄使用的列。
- **配置任意反射覆盖**：会破坏类型安全、网络确定性和版本升级。
- **预测所有东西**：敌方硬控、最终伤害、变身等错误预测的回滚体验与安全成本太高。

---

## 15. 最终设计准则

一套接近讲座思想、又符合 UE 5.8 GAS 能力边界的复刻架构，应满足：

1. ASC/Ability/Task/Effect/Cue 职责清晰，Ability 只是编排器。
2. 通用技能条目、专用多态配置、技能关系规则三态分离。
3. Timeline 是可预测、可取消、可在 Dedicated Server 执行的逻辑时间轴。
4. EffectTemplate、BuffSpec、CDR 将共性规则、实例数值、行为限制拆开。
5. Projectile、Scope、Summoned 走统一实体生命周期和网络策略。
6. 检测、生成、战斗数据访问全部管线化，并提供注册式扩展点。
7. 客户端预测只覆盖影响手感且可对账/可回滚的行为；服务器掌握最终结果。
8. 英雄独有机制写成代码能力，参数仍进入配置，不以英雄 ID 污染底层。
9. 编辑器提供数据溯源、网络预览和静态校验，而不只是集中展示属性。
10. 任何配置字段都必须有稳定语义、默认值、校验、版本和运行时所有者。

这套系统真正的核心不是“配置越多越好”，而是让**代码形成少量稳定的战斗原语，让配置安全地组合这些原语**。这也是《漫威争锋》能持续加入机制差异巨大的英雄，而不反复推翻整个战斗框架的关键。
