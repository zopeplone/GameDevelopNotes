# 《漫威争锋》AbilitySystem 配置结构详解

> 本文基于当前 FModel 导出的 `Marvel/Content/Marvel/AbilitySystem` 全量 JSON，以及 `Marvel/Content/Marvel/Data` 中与战斗相关的公共 DataTable 整理。
>
> 扫描结果：AbilitySystem 下 7,811 个 JSON 全部可解析；共发现 14 种 DataTable 行结构、1,116 个带 `MarvelAbilityItem` 的数字技能资产、1,141 个 Ability/EffectAbility 蓝图默认对象、1,232 个 `AnimTimeline`。导出中出现 4,604 个 `Type`，其中大量是每个蓝图自己的生成类，不等于 4,604 套公共配置结构。
>
> 本文解释的是**数据契约和资源关系**。FModel 能显示 Cook 后的默认值、类名和引用，但看不到原项目 C++ 函数体，也不能完整恢复 Blueprint EventGraph。凡是无法由导出数据确认的算法，本文会明确标注为推断或实现建议。
>
> “查看每个 Ability”在本文中指对全部技能资产做字段联合、类型频次和引用关系扫描，再逐一解释稳定的数据结构；不是把 1,116 个技能的具体数值逐行复制一遍。英雄独占 Config 会按公共族与代表性机制解释，因为大量 Type 只出现一次，其精确执行逻辑不在 JSON 中。

## 0. 配置系统的总图

一项技能并不是一个文件，而是一张由 ID 和资源引用串起来的图：

```text
MarvelHeroTable
  └─ HeroId
      ├─ MarvelHeroBaseAttributeTable
      │    ├─ AttrSpecs（形态、生命、盾、移速、额外 Attribute）
      │    └─ AmmoIDs
      │
      └─ MarvelAbilityTable（CompositeDataTable）
           └─ <Hero>_AbilityTable
                └─ FMarvelAbilityTableRow
                     ├─ AbilityID / CD / Charge / UI / Log
                     └─ AbilityAsset -> MarvelAbilityItem
                          ├─ GrantedAbility -> Ability_xxx_BP_C
                          ├─ ExtendConfigInline -> Config_xxx / PyConfig_xxx
                          ├─ TimelineToPlayMontage -> AnimTimeline
                          ├─ Input / Cost / Cooldown stage
                          └─ Cue / Camera / UI feedback

AnimTimeline 节点或 AbilityTask
  ├─ BuffId       -> MarvelBuffSpec -> MarvelEffectTemplate -> GameplayEffect
  ├─ ScopeId      -> MarvelScopeAgentTable
  ├─ ProjectileId -> MarvelProjectileAgentTable
  ├─ SummonerId   -> MarvelSummonerAgentTable
  └─ EquipId      -> MarvelEquipmentTable -> Weapon/ShootingLogic
                                         ├─ InstantAmmoId -> MarvelInstantAmmoTable
                                         └─ ProjectileId  -> ProjectileAgentTable
```

这套设计刻意把不同变化频率的数据拆开：

| 层 | 解决的问题 | 为什么不合并 |
|---|---|---|
| AbilityTable | 技能目录、CD、UI、统计 | 结构同构，适合批量查表和玩法覆盖 |
| MarvelAbilityItem | 一次技能的框架组装 | 需要引用 UObject、Timeline、输入和表现资产 |
| Ability BP | GAS 激活、Tag、网络和编排逻辑 | 属于可执行类，不只是数值 |
| ExtendConfig | 某类技能独有参数 | 飞行、枪械、传送门无法共享一张宽表 |
| Timeline | 逻辑事件在何时发生 | 时间编排与技能静态信息变化维度不同 |
| Buff/Scope/Projectile/Summoner | 可复用战斗原语 | 多个技能可引用同一原语，实体还需独立网络策略 |
| EffectTemplate | Buff 的共性状态规则 | 避免每个 Buff 重复配置驱散、叠层和 Cue |

## 1. 文件、ID 与引用规则

### 1.1 英雄目录

典型目录如下：

```text
AbilitySystem/1014/
  1014_Table/
    1014_AbilityTable.json
    1014_BuffSpecTable.json
    1014_CueOptTable.json
    1014_EquipmentTable.json
    1014_FlyConfigTable.json
    1014_InstantAmmoTable.json
    1014_ProjectileAgentTable.json
    1014_ScopeAgentTable.json
    1014_SummonerAgentTable.json
  101431/
    101431.json
    Ability_101431_BP.json
    Timeline_*.json
    Weapon / Ammo / Camera / Curve / Cue ...
```

`1014` 是英雄 ID，`101431` 是技能 ID。Scope、Projectile、Buff、Summoner 等通常使用更长 ID，例如 `10143101`。这个编码方便人看出所属英雄/技能，但运行时代码不应依赖字符串截位来推断关系，应以显式字段和注册表为准。

### 1.2 软引用对象结构

FModel 中 UObject 引用通常导出为：

```json
{
  "ObjectName": "MarvelAbilityItem'101431'",
  "ObjectPath": "/Game/Marvel/AbilitySystem/1014/101431/101431.1"
}
```

- `ObjectName`：对象类型与对象名。
- `ObjectPath`：包路径及包内 Export 索引。
- `null`：没有显式配置，通常使用类默认值或没有该能力。

复刻时建议用 `TSoftObjectPtr`/`TSoftClassPtr` 保存内容引用，用强类型 ID 保存战斗数据引用，不要在运行时拼字符串路径。

### 1.3 CompositeDataTable

公共的 `MarvelAbilityTable`、`MarvelBuffSpecTable`、`MarvelScopeAgentTable`、`MarvelProjectileAgentTable`、`MarvelSummonerAgentTable`、`MarvelInstantAmmoTable`、`MarvelFlyConfigTable`、`MarvelCueOptTable` 都是 `CompositeDataTable`。它们的 `ParentTables` 指向 Common、各英雄、Level、活动或玩法子表。

为什么需要它：

- 英雄团队只维护自己的子表；
- 公共系统只查一个聚合入口；
- 玩法可以附加或替换行；
- 资源依赖和 Cook 边界更清晰。

要注意：UE CompositeDataTable 对重复 RowName 的覆盖顺序敏感。复刻时必须规定父表顺序、重复 ID 规则，并在 CI 输出“哪张表覆盖了哪一行”，否则热更很难追踪。

### 1.4 与讲座 AbilitySet/AbilityPriority 的对应

当前导出中没有发现一个统一以 `AbilitySet` 命名、包含全部职责的公共对象。讲座所说的 AbilitySet 职责，在资源上主要由 `AbilityTableRow + MarvelAbilityItem` 承担；这是一种职责映射，不能据此断言原 C++ 类名。

AbilityPriority 则可在 `MarvelAbilityItem.ActivateData` 引用的 `AbilityActivateData_Base` 中观察到：

- `ActivatePriorityType`：BoundAbility、SelectAbility、LevelInteractiveAbility、CustomPriority 等类别；
- `InputBindConflict`：同一语义输入冲突时的处理；
- `Priority`：显式数值优先级。

它与 Ability BP 的 Block/Cancel Tag 配合：前者解决同一输入、选择态、关卡交互的竞争，后者解决已经激活后的技能关系。

## 2. `FMarvelAbilityTableRow`：技能目录行

### 2.1 它做什么

这是技能的**可检索总目录**。当前扫描到 126 张相关表、约 1,203 行。它不保存具体执行流程，而是把 Hero、AbilityID、CD、充能、UI、日志和 `MarvelAbilityItem` 关联起来。

### 2.2 字段结构

#### 身份与开关

| 字段 | 含义 | 配置方式 |
|---|---|---|
| `AbilityID` | 技能稳定 ID，通常也作为 RowName | 全局唯一；不要复用已发布 ID |
| `HeroName` | 所属英雄的文本/标识 | 用于编辑与日志，不应用它做权威归属判断 |
| `TName` | 本地化技能名 | FText/StringTable 引用 |
| `bEnable` | 是否启用 | 灰度、废弃或玩法禁用时使用 |
| `AbilityUser` | 使用者类别，如 Hero | 用于区分英雄、关卡实体、召唤物等 |
| `AbilityAsset` | 指向 `MarvelAbilityItem` | 必须与 AbilityID 对应并通过引用校验 |
| `bCacheSkill` | 是否缓存技能资源/实例 | 高频技能可开启，需结合内存预算 |

#### 输入与冷却

| 字段 | 含义 |
|---|---|
| `ActivateInput` | 面向 UI/旧输入层的键位描述，如 MouseLeft、E、Passive |
| `AbilityCD` | 基础冷却秒数 |
| `AbilityCDID` | 冷却组 ID；多个技能可共享同一冷却容器 |
| `bSaveCDInPlayerState` | CD 是否随 PlayerState 保存，换 Pawn/形态时不丢失 |
| `bSharedCDInTeam` | 是否为队伍共享 CD |
| `bKeepCDWhenReborn` | 重生后是否保留剩余 CD |
| `bIgnoreSaveEnegy` | 与保存能量/资源的项目规则有关；拼写来自导出 |

`AbilityCD` 是“显示/基础配置”，真正提交时机由 `MarvelAbilityItem.CommitCooldownStage` 决定，真正的 GAS 冷却通常仍由 GameplayEffect/Tag 实现。

#### 充能

| 字段 | 含义 |
|---|---|
| `MaxChargeCount` | 最大充能层数 |
| `ChargeInterval` | 每层恢复间隔 |
| `ChargeID` | 充能资源/组 ID |
| `ChargeAutoRemove` | 相关充能是否按规则自动移除 |

为什么单独有 ChargeID：同一技能可以换形态或被不同 Ability 触发，但共享一套次数；也可以让多个按钮消耗同一资源池。

#### 描述、UI 与反馈

| 字段 | 含义 |
|---|---|
| `Description` | 技能描述 |
| `PersonDescription` | 第一/第三人称或角色口吻相关描述 |
| `AbilityUITags` | UI 分类 Tag，如武器、被动、终极技能 |
| `QuoteBuff` | UI/逻辑需要展示或引用的 Buff |
| `BeHitAnimConfigID` | 命中反应配置 ID |
| `ImpulseLevelInfo` | 冲量等级及偏移 |
| `ImpulseApplyFilter` | 是否对小/大可破坏物、物理体、可投掷物施加冲量 |
| `DamageTypeClass` | 伤害类型/破坏等级类 |

#### 战斗日志与统计

| 字段 | 含义 |
|---|---|
| `AbilityLogTags` | 统计分类 Tag，如 Projectile、MainAttack |
| `AbilityRedirectLog` | 把伤害、治疗等统计重定向到另一展示项 |
| `AbilityLog` | 详细统计键与统计类型映射 |
| `BuffLog` | 此技能关心的 BuffID 列表 |
| `ForbiddenAbilityBaseLog` | 禁止的默认日志类别 |
| `ToRecordEffectIDs` | 需要单独记录的 EffectID |
| `AbilityStatisticsClass` | 自定义统计类 |
| `AbilityExtraStatisticsClass` | 额外统计扩展类 |

为什么日志不直接写在伤害代码里：同一个技能可能由投射物、召唤物、Buff 周期伤害共同产生结果，必须用稳定 ID 和重定向规则汇总。

#### 交付字段

`Delivery` 大量出现在表行末尾，看起来属于项目的数据交付/发布门控，而不是 GAS 原生字段；但仅凭 JSON 不能确认 true/false 在构建、热更或编辑器中的精确语义。复刻项目可用显式的 `bEnabledInBuild`、DataRegistry Meta 或资产管理规则实现类似职责，不要让战斗逻辑直接猜测该字段。

### 2.3 配置示例

以惩罚者 `101431`“审判者”为例：AbilityTable 行负责名字、MouseLeft、CD 和 AbilityAsset；真正的主武器 FireMode、输入资产和射击逻辑在 `101431.json` 与 Equipment/Ammo 中。这正是目录行保持简洁的原因。

## 3. `MarvelAbilityItem`：技能框架组装资产

### 3.1 它做什么

`MarvelAbilityItem` 是一个技能的框架配置中心。全量扫描到 1,116 项。它回答：

- 授予哪个 GameplayAbility 类；
- 用什么输入激活、确认、取消或触发内部方法；
- 播放哪些 Timeline；
- Cost 和 CD 在哪个技能阶段准备/提交；
- 需要哪些通用资源条逻辑；
- 触发哪些 Cue、镜头、命中反馈与 UI 反馈；
- 专用参数对象是哪一个。

### 3.2 核心引用

| 字段 | 含义 | 是否常见 |
|---|---|---:|
| `GrantedAbility` | 实际授予 ASC 的 Ability 类 | 1,116/1,116 |
| `ExtendConfigInline` | 专用 Config 子对象 | 1,052 |
| `TimelineToPlayMontage` | Timeline 与 AnimResIndex 列表 | 805 |
| `GrantedAbilityDataSet` | 额外授予的数据集 | 极少数 |

`TimelineToPlayMontage` 的每项包含：

- `Timeline`：`AnimTimeline` 对象引用；
- `AnimResIndex`：同一技能/形态的动画资源槽索引。

一个技能可以有多条 Timeline，例如开始、循环、结束，或者不同武器/形态使用不同索引。

### 3.3 输入结构

#### `ActivateInput`

观察到的子字段：

| 字段 | 含义 |
|---|---|
| `InputBind` | 语义输入枚举，如 PrimaryAttack、Ability1、Ultimate、Passive |
| `SkillActivationMode` | Click/默认、Hold、DoubleClick 等 |
| `bTriggerOnRelease` | 是否松开触发 |
| `MaxHoldTime` | 最大按住时间 |
| `AutoTriggerTime` | 到时自动触发 |

输入分布中 PrimaryAttack、Passive、SecondaryAttack、Ability1/2、Ultimate 最常见。`Passive` 也被建模为 Ability，说明被动初始化、监听和状态生命周期复用了 GAS。

#### `BindInputConfigs`

这是较新的、直接绑定 Enhanced InputAction 的结构：

| 字段 | 含义 |
|---|---|
| `BindType` | 激活 Ability、转发输入方法等绑定类型 |
| `SkillActivationMode` | Click/Hold/DoubleClick |
| `MethodName` | 不激活新技能，而是调用当前 Ability 内方法时使用 |
| `BindInputAction` | 键鼠 Enhanced InputAction |
| `GamepadInputAction` | 可单独覆盖手柄 InputAction |
| `bShouldUseSpecialAction` | 是否走特殊动作输入 |
| `bBlockOtherInput` | 触发后是否屏蔽其他输入 |
| `DelayTriggerTime` | 延迟触发 |
| `TriggerBlockedTags` | 拥有这些 Tag 时不能触发 |
| `TriggerBlockedTags_Blocking` | 阻挡态使用的 Tag 集 |
| `bUseIgnoreInputTemplateMask` / `IgnoreInputTemplateMasks` | 忽略某些输入模板 |
| `ActionTipsParam` | UI 输入提示、对齐、状态和优先级 |

#### `BindInputs`

这是技能激活后的内部输入绑定：

- `MethodName`：如 PlaceActor、Confirm、Release 等业务回调；
- `InputConfig`：InputBind、激活模式、松开触发、按住时间；
- `bBlockAbilityInput`：内部操作期间是否阻挡技能输入；
- `DelayTriggerTime`；
- `BindInputActionTipsParam`：对应 UI 提示。

传送门这种“按技能键进入放置态，再用主攻击放置”的技能需要它。只用一个 Ability 输入枚举无法描述这种状态内输入。

#### 确认、取消与候补输入

| 字段 | 含义 |
|---|---|
| `ConfirmInput` / `CancelInput` | 选择或放置态的确认、取消键 |
| `ConfirmTipsParam` / `CancelTipsParam` | UI 提示 |
| `CancelInputDelayTime` | 防止激活键同帧又触发取消 |
| `StandByActivateInput` | 候补/预激活输入 |
| `BlockInputBinds` / `KeyBoardBlockInputBinds` | 技能期间屏蔽的输入集合 |
| `KeyConsumptionPriority` | 同一输入被多个系统监听时的消费优先级 |

### 3.4 技能阶段、Cost 与 CD

项目把技能流程划分为 `Active`、`Missile`、`Break`、`End`、`Custom`、`TagEvent` 等阶段。

| 字段 | 含义 |
|---|---|
| `ReadyCostStage` | 何时准备/检查 Cost |
| `CostAttrActions` | 在指定阶段对资源执行操作 |
| `CommitCooldownStage` | 何时正式提交 CD |
| `ReadyCooldownStage` | 何时准备冷却 Spec/状态 |
| `*StageTag` | 由 GameplayTag 事件标识的自定义阶段 |
| `bCommitCooldownOnDeathInterrupt` | 死亡打断时是否仍提交 CD |

`CostAttrActions` 每项含：

- `AbilityStage`：在哪个阶段执行；
- `CostAction`：项目枚举/位掩码；导出常见数值为 1、8、16、32；没有原项目枚举声明，不能安全地给这些数字强行命名；
- `CustomTagEvent`：`TagEvent` 阶段的事件 Tag。

常见阶段分布显示 Cost 多在 `Missile`、`End`、`Active`、`Break` 执行，CD 最常在 `Break` 提交。这允许“按下进入瞄准不扣资源，真正发射才扣”“中途取消是否进 CD”等细粒度规则。

### 3.5 通用资源条/持续消耗

| 字段 | 含义 |
|---|---|
| `CostClipTypeTag` | 资源类型 Tag，如特殊能量/弹药槽 |
| `InitValue` / `MaxValue` | 初始值与最大值 |
| `ActivateCostValue` | 激活消耗 |
| `CheckActivateCostValue` / `MinimalActivateCostValue` | 最低激活门槛 |
| `ReduceValue` | 持续减少速率/数值 |
| `RegenValue` | 恢复速率/数值 |
| `RecoverDelayTime` | 停止消耗后的恢复延迟 |
| `bInitActiveCost` | 初始化时是否进入消耗态 |
| `bDefaultRegen` | 默认是否恢复 |
| `bRestartRegenWhernCost` | 再次消耗时重置恢复计时 |
| `bEndWithoutEnoughEnergy` | 资源不足时结束 Ability |
| `bCanActiveWithoutEnoughEnergy` | 允许低于通常阈值激活 |
| `bSlackCheckActivateCost` / `SlackCheckCostTime` | 宽松资源检查窗口，改善网络/输入体验 |
| `CostRequireTag` / `CostIgnoreTag` | 有/无指定状态时才执行 Cost |
| `PrimaryCost` | 是否为主要资源 UI/结算项 |
| `bFollowIgnoreCost` | 跟随项目级“忽略消耗”规则 |

这些字段看似可直接替代 GAS Cost GE，但更合理的理解是：项目用一个通用资源控制层生成/提交 GAS Cost，并驱动 UI 和持续技能。权威数值仍应落在 ASC Attribute/GameplayEffect 上。

### 3.6 Combo

`AbilityComboSections` 的每项包含：

- 是否要求命中；
- 命中、未命中、被打断时跳到哪个 ComboID；
- 打断发生在 Missile 前后是否重置；
- Combo 超时时间。

配套字段还有：

- `bUsingDifferentComboRange`；
- `HighlightComboScopes`；
- `bChooseCameraShakeByCombo`；
- `HitEnemyCameraShakeClassesByCombo`。

为什么放在 AbilityItem：Combo 是技能框架的通用状态机，不应由每段攻击蓝图各自维护整数计数和计时器。

### 3.7 Cue、镜头与命中反馈

| 字段 | 含义 |
|---|---|
| `AbilityGameplayCues` | CueTag、添加阶段、移除阶段、预测 Cue 清理策略 |
| `CameraInterpAsset` / `AutoActiveCameraInterp` | 技能镜头插值资产及自动激活 |
| `AbilityCameraShakeClass` | 技能自身镜头震动 |
| `HitCameraShakeClass` | 命中后的本地镜头震动 |
| `HitEnemyCameraShakeClass` | 被命中敌人的镜头震动 |
| `EnableCameraShake` / `AcivateAbilityShake` | 震动开关与激活反馈 |
| `HitCharactersAndNonShieldSummons` | 命中角色/非盾召唤物是否反馈 |
| `HitShieldSummons` | 命中盾类召唤物是否反馈 |
| `HitScenes` / `HitDestructibleScenes` | 场景与可破坏物反馈 |
| `AutoShakeHUD` / `ShakeHUDType` | 在某阶段触发 HUD 动画 |
| `EnableAnimFrameFreeze` / `AnimFrameFreezeConfig` | 命中停顿；可分别配置敌人/场景的速率和持续时间 |
| `ScopeIDNeedHighlight` | 需要高亮显示命中/范围的 ScopeID |
| `PPTransparentDistanceOffset` | 近距离后处理透明相关偏移 |

表现字段可以预测，伤害结果不能由这些开关决定。CameraShake 和 HUD 必须限定在本地玩家，Dedicated Server 不应加载或运行。

### 3.8 失败反馈与循环技能

| 字段 | 含义 |
|---|---|
| `bDisableAudioOnFailBlock/Cooldown/Cost/UserLogic/OtherCanActivate` | 按失败原因禁用默认错误音 |
| `CustomActivateInterval` | 自定义重复激活间隔 |
| `bStopLoopActivateWhenUserCancel` | 用户取消时停止循环激活 |
| `CancelLoopAbilityActions` | 循环技能取消时执行的动作 |
| `AutoBeginGather` / `GatherCallbackValues` | 自动进入蓄力/收集流程与回调值 |
| `bReplicateDataSet` | 是否复制技能数据集 |

## 4. `Ability_*_BP_C`：GAS Ability 类默认配置

### 4.1 它与 AbilityItem 的区别

AbilityItem 是数据和资产组装；Ability BP 是可执行 `UGameplayAbility` 派生类。前者可以更换输入、Timeline、数值，后者决定 `ActivateAbility` 如何创建 Task、响应 Timeline 事件和清理状态。

1,141 个 Ability/EffectAbility 蓝图中，最稳定的公共字段是：

| 字段 | 观察次数 | 作用 |
|---|---:|---|
| `AbilityTags` | 1,084 | 技能自身类别 |
| `ActivationOwnedTags` | 1,057 | 激活期间授予拥有者的 Tag |
| `BlockAbilitiesWithTag` | 712 | 激活时阻挡的技能类别 |
| `CancelAbilitiesWithTag` | 706 | 激活时取消的技能类别 |
| `bIsCancelable` | 382 | 能否被外部/输入取消 |
| `ActivationRequiredTags` | 292 | 必须拥有的状态 |
| `IsLoopAbility` | 285 | 是否循环 Ability |
| `AbilityLabels` | 261 | 项目业务标签 |
| `ActivationBlockedTags` | 260 | 拥有即不能激活的状态 |
| `ReplicationPolicy` | 260 | Ability 实例复制策略 |
| `NetExecutionPolicy` | 163 | 本地预测/服务器执行策略 |
| `ActivationRequiredAnyTags` | 120 | 满足任一即可的项目扩展 |

### 4.2 Tag 关系怎么配置

建议按职责建 Tag：

```text
Ability.Type.Attack.Primary
Ability.Type.Move.Dash
Ability.State.Aiming
State.Control.Stunned
State.Disable.Move
Ability.Event.Missile
Ability.Event.Break
```

- `AbilityTags` 描述“我是谁”；
- `ActivationOwnedTags` 描述“我运行时角色处于什么状态”；
- Required/Blocked 描述“什么状态下可以启动”；
- Block/Cancel 描述“我启动后如何影响别的技能”。

不要用 AbilityID 互相硬引用来处理所有打断关系。Tag 类别规则能让新技能自动参与；只有确实独特的冲突才使用显式配置。

### 4.3 阶段取消扩展

导出中可观察到：

- `PreMissileStageConfig`、`MissileStageConfig`、`BreakStageConfig`；
- `PreMissileCancelConfig`、`MissileCancelConfig`、`BreakCancelConfig`；
- `ConsistentCancelConfig`；
- `CancelAllowedConfigType`、`CancelAllowedPolicy`；
- `EnterBreakRemoveActivateBlockTags`；
- `CancelWithOwnerTagAdd/Remove`。

它们说明项目没有把“可取消”简化为一个布尔值，而是按前摇、出手、生效、后摇阶段定义窗口。配置时必须回答：

1. 谁可以取消我；
2. 哪个阶段可以取消；
3. 取消后跳 Break、End 还是另一 Timeline Section；
4. 是否提交 Cost/CD；
5. 哪些临时 Tag/Cue/预测实体需要清理。

### 4.4 网络策略

显式导出的 `NetExecutionPolicy` 分布：ServerInitiated 126、ServerOnly 34、LocalOnly 3，其余 978 项继承父类默认值。**字段未导出不表示 ServerOnly，也不表示 LocalPredicted**，只能说明没有覆写 CDO 默认值。

- 玩家直接操作、可回滚的技能通常使用 LocalPredicted 父类；
- AI、环境、被动触发可用 ServerInitiated；
- 权威生成、不可预测逻辑用 ServerOnly；
- LocalOnly 只能承载纯本地表现/辅助，不能改权威战斗状态。

### 4.5 蓝图私有变量

导出中还有大量只出现一次的中文/英文变量。这些是具体 Blueprint 的私有状态或兼容旧实现，不属于公共数据契约。复刻时不要把它们全部搬进公共基类；能迁移到 `ExtendConfig` 的静态参数迁移，计时器、Handle、运行时缓存留在 Ability 实例。

## 5. `ExtendConfigInline`：技能专用多态配置

### 5.1 为什么必须多态

扫描数字技能资产得到 675 种非 AbilityItem Type。许多是英雄独占 `PyConfig_103751` 之类的结构；若把所有字段放进 AbilityTable，会出现上千列、绝大多数为空，并造成模块互相依赖。

正确模式是：

```text
MarvelAbilityConfig（公共基类）
  ├─ 射击模板配置
  ├─ 跳跃/飞行/Dash 配置
  ├─ 选择目标配置
  ├─ 召唤/投射物/Scope 引用配置
  └─ 英雄专用 Config
```

### 5.2 可复用基类/族

| 类型 | 主要字段 | 用途 |
|---|---|---|
| `MarvelAbilityConfig` | AbilityDuration、Debug Trace/Print | 最小公共配置与调试 |
| `AbilityActivateData_Base` | ActivatePriorityType、InputBindConflict、Priority | 同输入竞争、选择/互动技能优先级 |
| `Config_105` | EquipID、FireModeIndexes、RoundRobin、松开延迟、曲线 | 连续/轮换武器射击 |
| `Config_106` | EquipID、FireMode、ShootCount/Delay、MontagePlayMode | 一次或分批开火 |
| `Config_107` | AmmoTags、自动换弹技能、取消 Tag、用户设置 | 换弹/自动换弹 |
| `Config_AeroBase` | FlyModeID、持续时间、自动下降、最低高度 | 飞行/悬浮 |
| `MarvelAbilityConfig_DoubleJump` | 水平/垂直速度、重力 Buff、覆盖开关 | 二段跳 |
| `MarvelAbilityConfig_AbilityJump` | 跳跃速度、结束规则 | 单次技能跳 |
| `Config_HighJump` | 额外前向/向上速度 | 高跳 |
| `MarvelAbilityConfig_LongPressTrigger` | 等待状态、TaskParam、FlyModeID | 长按/蓄力 |
| `SelectAbilityConfigBase` | SelectParam、AbilityActions | 选择目标后执行动作 |
| `SelectAbilityConfigBase_Bond` | Bond 目标数据、Buff 阶段、过滤委托 | 连携技能选择 |
| `Config_PhantomInputSyncAbility` | SyncAbilityConfigs | 分身/幻象同步输入 |
| `WallRunningPassiveAbilityConfig` | 上墙参数、AbilityID、按键 | 被动爬墙入口 |
| `WallRunningAbilityConfig` | 顶部 Dash、跳离、Buff、速度 | 墙跑执行 |
| `MarvelBackTrackConfig` | 回溯时间、移动模式、盾转换、Trace | 回到历史位置 |

### 5.3 专用配置如何读

专用 Config 的字段应按“引用 + 算法参数”理解：

- `ScopeID/ProjectileID/SummonerID/BuffID/AbilityID/EquipID`：引用通用原语；
- Radius/Distance/Duration/Speed/Curve：给专用算法的参数；
- Tag/TagRequirements：状态与过滤；
- TaskParam/DashInfo/SelectParam/TraceContext：嵌套公共行为结构；
- Camera/Audio/Cue：本地表现；
- `bShould...`：选择一个已经由代码实现的策略分支。

例如：

- 奇异博士 `Config_101861` 配放置相机、Portal Trace 半径、碰撞通道、预览 Actor 和持续时间；空间变换和跨门 Trace 算法不在配置里。
- 万磁王 `PyConfig_103751` 配吸收类型、检测体、频率、时长和恢复映射；接管投射物生命周期必须由代码完成。
- 美国队长 `PyConfig_102241` 配反射方向类型、散布、衰减、额外伤害 Scope 和 Buff；重写阵营、Instigator 与后续轨迹是代码职责。

### 5.4 如何设计自己的 ExtendConfig

```cpp
USTRUCT(BlueprintType)
struct FAbilityTemplateConfigBase
{
    GENERATED_BODY()
    UPROPERTY(EditAnywhere) float AbilityDuration = 0.f;
};

USTRUCT(BlueprintType)
struct FProjectileAbilityConfig : public FAbilityTemplateConfigBase
{
    GENERATED_BODY()
    UPROPERTY(EditAnywhere) FProjectileId ProjectileId;
    UPROPERTY(EditAnywhere) int32 Count = 1;
    UPROPERTY(EditAnywhere) float Interval = 0.f;
};
```

顶层用 `FInstancedStruct` 或多态 DataAsset 保存。每个模板只接受自己声明的 Config 类型；加载时校验 AbilityClass、TemplateType 与 Config ScriptStruct 一致。

## 6. `AnimTimeline`：技能逻辑时间轴

### 6.1 主结构

`AnimTimeline` 不是 Actor `UTimelineComponent`。主字段为：

| 字段 | 结构 |
|---|---|
| `AnimNotifyTracks` | Track 数组，每条含 Version、TrackName、TrackColor、Notifies |
| `AnimSections` | SectionName、NextSectionName、Time、Version |
| `SequenceLength` | 逻辑时间轴总长 |
| `MontagePath` | 配合播放的 Animation Montage |
| `bFastTickOnActive` | 激活时是否使用更高频/快速 Tick |
| `bStopAutomatically` | 到末尾是否自动停止 |
| `AssetUserData` | 扩展元数据 |

每个 Notify 记录：

- `NotifyName`；
- `StartTime`、`Duration`；
- 起止 TriggerTimeOffset；
- `TrackIndex`、颜色、版本与 Identity；
- `NotifyObject`（瞬时节点）或 `NotifyStateClass`（区间节点）。

### 6.2 公共节点全集

| 节点类型 | 字段 | 做什么 |
|---|---|---|
| `MarvelTagNotify_Missile` | EventTag、Payload | 标记真正出手/生效阶段 |
| `MarvelTagNotify_Break` | Payload | 进入后摇/打断收尾 |
| `MarvelTagNotify_Begin/End` | EventTag、Payload | 通用开始/结束阶段 |
| `MarvelTagNotify_Pick/Select` | EventTag、Payload | 选择/拾取流程 |
| `MarvelTagNotify_Reload` | Payload | 换弹关键点 |
| `MarvelTagNotify_EndAbility` | Payload | 显式结束 Ability |
| `AnimNotify_TagNotify` | EventTag、Payload | 发任意 GameplayTag 事件 |
| `AnimNotify_SpawnScope` | ScopeId、Socket、Offset、Rotation、Predict | 创建/执行 Scope |
| `AnimNotifyState_TimedScope` | ScopeId、位置 | 区间内维持检测 |
| `AnimNotify_SpawnProjectile` | ProjectileId、Socket、Offset | 发射 Projectile |
| `AnimNotify_SpawnSummoner` | SummonerId、Socket、Offset | 生成召唤物 |
| `AnimNotifyState_TimedSummoned` | SummonerId | 区间绑定召唤物 |
| `AnimNotify_ApplyBuff` | BuffId、DurationOverride、ValueOverride | 施加 Buff |
| `AnimNotifyState_ApplyBuff` | BuffId | 区间 Buff |
| `AnimNotify_RemoveBuff` | BuffId、是否检查 Instigator | 移除 Buff |
| `AnimNotifyState_TimedOwnedTags` | GameplayTags | 区间授予角色 Tag |
| `AnimNotifyState_TimedBlockTags` | AbilityBlockTags、AbilityCancelTags | 区间改变技能关系 |
| `AnimNotify_AddTags/RemoveTags` | GameplayTags | 瞬时增删 Tag |
| CameraShake / CameraInterp | ShakeClass/InterpAsset/本地开关 | 镜头表现 |
| WeaponEvent | EquipID、Begin/End EventTag | 驱动武器状态 |
| `AnimNotify_AbilitySocketInfo` | Id、Socket、位置类型/偏移 | 缓存逻辑发射点 |
| `AnimNotify_RecoveryCost` | 无显式字段 | 资源恢复节点 |
| `AnimNotify_RefreshCooldown` | RefreshCDParams | 刷新 CD |
| `AnimNotify_ApplyDash_WithFilter` | DashInfo、TagRequirements | 条件位移 |
| `AnimNotifyState_TimedChangeCapsuleSize` | Radius、HalfHeight、Mesh Offset | 区间改碰撞体 |

少量以英雄命名的 Notify 是专用扩展，例如黑猫资源、凤凰事件、潘妮特殊动画状态。它们应调用英雄组件/接口，不应让 Timeline 运行器依赖英雄 ID。

### 6.3 配置原则

- 权威伤害/生成节点必须在服务器 Timeline 执行；Montage 只负责动画同步。
- Cue、Camera 节点可以在拥有客户端预测执行，并用 PredictionKey/事件序号去重。
- 区间节点必须实现取消清理；中途 EndAbility 时要调用仍激活节点的 End。
- Section 跳转、播放速率、掉帧补帧必须保持确定顺序。
- `StartTime` 相同的节点要有稳定排序规则，不能依赖 TArray 偶然顺序。

## 7. `MarvelEffectTemplate`：Buff 的共性模板

### 7.1 它做什么

公共表当前包含约 209 个 EffectTemplate 行。它定义“某一类状态通常如何运行”，例如正面数值、负面数值、硬控、逻辑状态、关卡效果。具体英雄数值不放这里，而由 BuffSpec 覆写。

当前 `TypeTag` 分布可观察到：SpecialEffect 65、NegativeEffect 43、PositiveEffect 36、NumericalBuff 31、LogicalEffect 21、NumericalDebuff 10，另有少量 LevelEffect/Activating/None。

### 7.2 身份与分类

| 字段 | 含义 |
|---|---|
| `ID` | Effect 模板 ID |
| `TName` / `NameText` | 编辑名与本地化名 |
| `EffectTag` | 稳定状态 Tag，如 `Effect.1109` |
| `TypeTag` / `TypeDesc` | 正面、负面、数值、逻辑、特殊等分类 |
| `Desc` | 设计说明 |
| `StatusTags` | 此模板代表的细粒度状态 Tag |
| `AssetTags` | 来源、音频、伤害辅助等资产分类 |
| `GrantTags` | 应授予目标的附加 Tag |

为什么同时有 EffectTag、TypeTag、StatusTag：

- EffectTag 唯一标识一个模板；
- TypeTag 用于驱散/免疫整类效果；
- StatusTag 驱动移动、动画、输入等下游系统；
- AssetTag 描述来源或表现属性，不一定成为目标 OwnedTag。

### 7.3 持续、数值与周期

| 字段 | 含义 |
|---|---|
| `DurationPolicy` | Instant、HasDuration、Infinite |
| `AttributeTag` | 默认修改哪个 Attribute |
| `ModifierOp` | Additive、Multiplicative、Override 等 |
| `Period` | 周期执行间隔 |
| `EffectPriority` | 效果关系优先级 |
| `EffectTemplate` | 指向实际 GameplayEffect 蓝图类 |

模板只保存“默认修改方式”。具体数值来自 BuffSpec 的 `AttributeValue`，通常通过 SetByCaller 写入 GE Spec。

### 7.4 状态关系

| 字段 | 含义 |
|---|---|
| `BlockStatus` | 目标有这些状态时阻止应用，或本状态阻挡它们 |
| `BlockStatusIgnoreTagQuery` | 满足 Query 时忽略阻挡关系 |
| `DispelStatus` | 应用时驱散哪些状态 |
| `DispelStatusTagQuery` | 通过复杂 TagQuery 选择驱散对象 |
| `BeDispelledStatus` | 能被哪些状态/类别驱散 |
| `InhibitedStatus` | 哪些状态让本 Effect 暂时 Inhibit |
| `RequireStatus` | 应用前必须存在的状态 |
| `Coexist` | 与同类/替换对象是否允许共存 |

`FGameplayTagQuery` 在 JSON 中由 `TagDictionary + QueryTokenStream` 编码，`AutoDescription/UserDescription` 只用于编辑器展示。不要手写 TokenStream；应通过 UE TagQuery 编辑器构造。

### 7.5 叠层与生命周期

| 字段 | 含义 |
|---|---|
| `StacksRule` | NoStack、BySource、ByTarget、Replace 等项目规则 |
| `StackLimitCount` | 最大层数；0/-1 的精确语义由项目规则决定 |
| `DenyOverflow` | 达上限后拒绝新应用 |
| `RefreshStackTime` | 新层是否刷新持续时间 |
| `bModifierCleanAutoRemove` | Modifier 清理时自动移除 |
| `bOwnerDeathAutoRemove` | 目标死亡时移除 |
| `bCanAppliedWhenDeath` | 死亡目标能否被施加 |
| `bTerrainDeathRelevancy` | 是否参与地形死亡规则 |
| `SyncRadius` | 该状态/表现的同步半径 |

### 7.6 Cue 与授予 Ability

| 字段 | 含义 |
|---|---|
| `GameplayCue` | 通用 Cue |
| `GameplayCue_Animation` | 动画表现通道 |
| `GameplayCue_FX` | Niagara/粒子通道 |
| `GameplayCue_UI` | UI 通道 |
| `GameplayCue_ScreenFX` | 屏幕特效通道 |
| `bEnableCullDistance` | 是否启用距离裁剪 |
| `EffectAbilties` | Buff 存在时授予的 Ability 列表；拼写来自导出 |

`EffectAbilties` 每项包含 Ability 类、AbilityID、是否立即激活一次、是否替换模板自带 Ability、移除策略。

### 7.7 韧性扩展

| 字段 | 含义 |
|---|---|
| `bIsResilienceProtected` | 是否受控制韧性保护 |
| `ResilienceIncrease` | 应用后增加的韧性/抗性 |

## 8. GameplayEffect 蓝图：EffectTemplate 的运行载体

### 8.1 为什么表外还要一个 GE 资产

EffectTemplate 是项目数据；GAS 最终只能通过 `UGameplayEffect`/`FGameplayEffectSpec` 修改 ASC。`EffectTemplate.EffectTemplate` 指向的 GE 蓝图负责把项目规则映射到 GAS 的 Duration、Tag、Stack 和 Component。

以 `Effect_1109` 导出为例，可以观察到：

- `DurationMagnitude` 使用 SetByCaller `CustomEffect.Duration`；
- Effect/Type/Status Tag 被写入 AssetTags 与 TargetTags；
- `CancelAbilitiesWithTag` 与 `BlockAbilitiesWithTag` 定义硬控关系；
- `RemoveGameplayEffectQuery` 定义互斥/驱散；
- `StackingType=Replace`、不共存、持续时间不刷新；
- GE 引用多个 `GameplayEffectComponent`。

### 8.2 UE 5.8 的 GE Component 结构

当前导出和 UE 5.8 源码都显示现代 GE 使用组件：

| Component | 作用 |
|---|---|
| `AssetTagsGameplayEffectComponent` | 定义 GE 自己的 AssetTags |
| `TargetTagsGameplayEffectComponent` | 给目标授予 OwnedTags |
| `TargetTagRequirementsGameplayEffectComponent` | 应用、持续、移除 Tag 条件 |
| `ImmunityGameplayEffectComponent` | 对匹配 Effect Query 的免疫 |
| `RemoveOtherGameplayEffectComponent` | 应用时移除其他 GE |
| `AbilitiesGameplayEffectComponent` | 持续期间授予 Ability |
| `BlockAbilityTagsGameplayEffectComponent` | 阻挡技能类别 |
| `CancelAbilityTagsGameplayEffectComponent` | 取消技能类别 |
| `AdditionalEffectsGameplayEffectComponent` | 连带施加其他 GE |
| `CustomCanApplyGameplayEffectComponent` | 项目自定义 CanApply 入口 |

旧教程常直接配置 `GrantedAbilities`、OwnedTags、ApplicationRequirements 等旧字段。UE 5.8 中应优先使用这些 Component；解包保留的旧字段可能是项目兼容层或序列化遗留。

### 8.3 配置流程

1. EffectTemplate 定义项目层规则。
2. 对应 GE 蓝图选择 DurationPolicy、SetByCaller Tag 和所需 GE Component。
3. BuffSpec 提供具体 Duration、Magnitude、Stack 覆盖。
4. 运行时构造 Spec，填 SetByCaller 和 Context。
5. 服务器应用到目标 ASC。

EffectTemplate、GE 蓝图和 BuffSpec 三者必须有自动一致性校验，例如模板说 HasDuration，但 GE 是 Instant，应在 Cook 前报错。

## 9. `FMarvelBuffSpec`：某技能的具体 Buff 实例

### 9.1 它做什么

扫描到 159 张 BuffSpec 表、约 2,643 行。EffectTemplate 回答“这是什么状态”，BuffSpec 回答“这次由哪个英雄以多大数值、多久、怎样叠层和表现来应用”。

### 9.2 身份与数值

| 字段 | 含义 |
|---|---|
| `ID` | BuffSpecID；通常也是 RowName |
| `HeroName` | 所属英雄/配置域 |
| `EffectID` | 引用 EffectTemplate |
| `Desc` | 策划说明 |
| `AttributeValue` | 主要数值/Magnitude |
| `AttributeDiffusion` | 数值随时间、距离或曲线扩散 |
| `ExtendedConfig` | 少量 Buff 的多态特殊配置 |
| `BuffAttributeType` | Normal、Treat、Damage |
| `Delivery` | 数据交付标记 |

`AttributeDiffusion` 观察到：

- `Mode`：扩散模式；
- `Origin`：扩散原点；
- `Period`：采样/周期；
- `AttributeCurve`：曲线；
- `CustomDiffusionCalculationClass`：自定义计算类。

这让同一 BuffSpec 能表达距离衰减、时间衰减或自定义曲线，而不必复制多行。

### 9.3 百分比伤害与治疗

| 字段 | 含义 |
|---|---|
| `PercentDamageHealthType` | 按当前/最大/其他生命类型计算的枚举 |
| `PercentDamagePercent` | 百分比伤害比例 |
| `PercentTreatType` | 百分比治疗基准 |
| `PercentTreatPercent` | 百分比治疗比例 |

这类值必须在服务器 Execution 中计算并设置上限/下限；不要让客户端直接提交最终数值。

### 9.4 Duration、Period 与 LifeWith

| 字段 | 含义 |
|---|---|
| `Duration` | 具体持续时间 |
| `Period` | 周期 Tick 间隔 |
| `bOverrideEffectLifeSpan` | 是否覆盖模板生命周期 |
| `bCanAppliedWhenDeath` | 覆盖死亡应用规则 |
| `bModifierCleanAutoRemove` | 覆盖清理规则 |
| `bOwnerDeathAutoRemove` | 目标死亡清理 |
| `LifeWith` | 绑定的生命周期对象集合 |

`LifeWith` 包含：

- `LifeWithAbility` / `LifeWithAbilityDestroy`；
- `LifeWithAlive` / `LifeWithTargetAlive`；
- `LifeWithCauser` / `LifeWithInstigator`；
- `LifeWithModifierClean`。

为什么需要 LifeWith：很多状态不是纯计时器。例如护盾跟随召唤物，区域 Buff 跟随 Ability，施法者死亡后消失。只配置 Duration 无法表达这些所有权关系。

### 9.5 叠层覆盖

| 字段 | 含义 |
|---|---|
| `bOverrideEffectStackRule` | 使用 BuffSpec 的叠层规则而非模板 |
| `StacksRule` | NoStack、BySource、ByTarget、Replace |
| `DenyOverflow` | 达上限是否拒绝 |
| `StackLimitCount` | 最大层数 |
| `StackingExpirationPolicy` | 整栈清除或逐层清除 |
| `StackPeriodResetPolicy` | 重叠后是否重置周期 |
| `RefreshStackTime` | 重叠后刷新持续时间 |
| `bUseRemainingMagnitudes` | 替换时是否保留剩余量 |
| `bRefreshWhenReplace` | Replace 时是否刷新 |
| `bAccumulateDuration` | 重复应用是否累加时间 |
| `MaxAccumulateDuration` | 最大累加持续时间 |
| `bBlockApplyFromDifferentSource` | 不同 Source 是否禁止共同叠层 |

观察分布：NoStack 约 1,591 行、BySource 633、Replace 341、ByTarget 12；绝大多数到期清整栈并在成功应用时重置 Period。这说明“同一个 BuffID”不等于相同实例，Source 是重要的聚合键。

### 9.6 预测与同步

| 字段 | 含义 |
|---|---|
| `bShouldPredictSpawn` | 客户端是否预测添加 |
| `bShouldPredictDelete` | 客户端是否预测删除 |
| `bInvalidSyncBuff` | 是否不作为常规同步 Buff |
| `SyncRadius` | 同步/表现相关半径 |

仅少数 Buff 开启预测 Spawn/Delete，符合“玩家自身可回滚资源/状态可预测，敌方硬控和最终伤害由服务器确认”的原则。

### 9.7 Ability、Tag 与 Cue

| 字段 | 含义 |
|---|---|
| `GrantedAbilties` | Buff 存在时授予 Ability，可覆盖模板 |
| `AssetTags` | BuffSpec 的资产/来源 Tag |
| `GrantTags` | 目标获得的 Tag |
| `BlockAbilityTags` | 用 TagRequirement 结构阻挡 Ability |
| `CancelAbilityTags` | 取消 Ability |
| `bOverrideEffectCues` | 覆盖模板 Cue |
| `GameplayCues` | Buff 具体 Cue 列表 |
| `bSuppressStackingCues` | 叠层时不重复触发 Cue |
| `bDisableCullDistance` | 禁止距离裁剪 |

`GrantedAbilties` 每项含 Ability 类、AbilityID、是否立即激活、替换模板标志和移除策略。

### 9.8 Buff 链与日志

| 字段 | 含义 |
|---|---|
| `BgnBuffIds` | 本 Buff 开始时联动添加的 Buff |
| `EndBuffIds` | 正常结束时联动 Buff |
| `BreakBuffIds` | 被打断/破坏时联动 Buff |
| `CustomBuffIds` | 自定义阶段联动 Buff |
| `NeedActionLog` | 是否记录行为日志 |
| `bTerrainDeathRelevancy` / `KillTerrainTime` | 与地形死亡相关 |

Buff 链必须做循环检测。`A End -> B`、`B Begin -> A` 会形成无限应用；加载时应建有向图检测环和最大链深度。

### 9.9 `ExtendedConfig`

全量联合字段中可见：伤害累积、护盾值、继承比例、衰减曲线、阶段参数、吸血比例、CD 缩减、盲视 Scope、TracePolicy、自定义 Magnitude 等。这些是少量模板的专用参数。

配置原则：

- 通用叠层/Duration/Tag 不应塞进 ExtendedConfig；
- 新字段若被多个 Buff 使用，应提升为公共结构或独立 GE Component；
- `LogicClass` 只选择代码策略，不允许配置任意脚本直接修改世界状态。

## 10. 多个表共享的嵌套战斗结构

### 10.1 `BaseDamage`

Scope、Projectile、InstantAmmo 都复用近似的伤害结构：

| 字段 | 含义 |
|---|---|
| `BaseValue` | 基础伤害 |
| `PercentDamageHealthType/Percent` | 百分比生命伤害 |
| `ExtraShieldDamage` / `TargetFlags` | 对特定盾类型的额外伤害 |
| `ApplyFilter` | Self/Enemy/Teammate 等作用阵营 |
| `ApplyRequirements` | 施加伤害所需 Tag 条件 |
| `DamageEffect` | 伤害 GameplayEffect/模板引用 |
| `DamageCurveParams` / `DamageCurve/2` | 距离、时间、蓄力等曲线参数 |
| `DiffusionOrigin2` | 衰减距离的原点/轴定义 |
| `CriticalStrikePer` | 暴击倍率 |
| `DamageRatio` | 最终比例 |
| `DamageRepeat` | 重复/多段倍率或次数参数 |
| `DamageCueTag` | 伤害表现 Cue |
| `DynamicAssetTags` | 写入 Spec 的动态来源 Tag |

计算顺序必须在代码中固定。例如先基础值与曲线，再倍率、暴击、护盾规则，最后防御/减伤。配置只提供输入，不能由不同 Scope 各自决定顺序。

### 10.2 `BuffApplyInfo`

Projectile 的 `BuffSpecs`、InstantAmmo 的 Buff 列表等常含：

- `BuffSpecId`；
- `BuffStackCount`；
- `ApplyFilter`；
- `ApplyRequirements`；
- `BuffDesc`；
- `bUniqueInstanceID`。

`bUniqueInstanceID` 用于同 BuffID 但需要独立生命周期/叠层键的命中，例如同一来源的多个区域实例。

### 10.3 `TagRequirements`

常见结构为：

- `RequireTags`；
- `IgnoreTags`；
- `bUseTagQuery`；
- `TagQuery`。

简单 AND/忽略关系用数组，复杂 AND/OR/NOT 用 TagQuery。配置 `bUseTagQuery=true` 时必须验证 Query 非空。

### 10.4 `TraceRule` / `CollisionRule`

规则通常按 Self、Teammate、Enemy、Scene 四类分别配置：

- 默认 Trace/Collision Type；
- 自定义 Trace/Collision 开关；
- 对应 TagRequirements；
- `CustomChannelPreset`；
- `TypeTag`；
- Scope/Ammo Trace 还可配 Head Check 模式和半径。

为什么 Source 规则和 Target Tag 都需要：Collision Channel 做物理粗筛，GameplayTag 做业务精筛。只用 Channel 会导致英雄特殊状态必须不断增加 Channel；只用 Tag 则每次查询候选过多。

### 10.5 `AgentQuote`

Scope/Projectile/Summoner/ChaosField 的 Quote 结构常含：

- `Spawn_AgentId`；
- `Effective_AgentId`；
- `MergeAgentId`；
- `Recylce_AgentId`；
- `MinOverlapPercentage`；
- `MinMegreCuePercentage`。

它描述实体生命周期阶段引用的其他 Agent：生成时、真正生效时、合并时、回收时。这样投射物可在命中时生成 Scope，Scope 可生成召唤物，实体可以组合而不把子逻辑写死在 Actor 类中。

### 10.6 冲量结构

- `ImpulseLevelInfo`：`CustomLevel`、`OffsetLevel`；
- `ImpulseApplyFilter`：是否作用于小/大可破坏物、PhysicsBody、Throwable；
- 公共 `MarvelImpulseTable`：ImpulseLevel、速度区间、伤害区间，以及死亡/布娃娃/场景的 MassImpulseCurve。

表把“技能配置的冲量等级”转换为按质量和目标类型计算的物理冲量。实际施力、网络和布娃娃切换必须由代码处理。

## 11. `FMarvelScopeAgentTableRow`：检测场、射线与范围效果

### 11.1 Scope 是什么

Scope 是统一的“空间查询 + 目标过滤 + 对结果施加伤害/Buff/Cue”配置。它既可以表示一帧射线，也可以表示持续球形法阵、扇形近战、盒体冲撞和胶囊范围。

扫描到 141 张 Scope 表、约 930 行。形状分布中 Sphere 679、Cylinder 95、Box 68、Sector 16、Line 9、Capsule 7、PhysicsFrustum 5。绝大多数为 `Multi_Overlap`，说明很多看似一次攻击也通过统一 Overlap Scope 实现。

### 11.2 身份、资产与生命周期

| 字段 | 含义 |
|---|---|
| `Id` | ScopeID |
| `HeroName` / `Desc` | 所属与说明 |
| `AssetTags` | Scope 类型/来源分类 |
| `ScopeAgent` | Scope 实体/组件和生命周期配置 |
| `ScopeQuote` | Spawn/Effective/Merge/Recycle 子 Agent 引用 |
| `ExtendedConfig` | 英雄或模式专用扩展 |
| `bOpenCache` | 是否进入对象/配置缓存 |
| `Delivery` | 发布标记 |

`ScopeAgent` 嵌套字段包括：

- Scope Actor/Agent 类与可读名；
- TraceComponent、EffectiveComponent 与可读名；
- `TraceDelay`、`TracePeriod`、`TracePolicy`；
- `LiftTime`（导出拼写）与 `LifeWith`；
- 数量限制、回收延迟；
- Quote 类型与落点偏移。

为什么 Scope 可以有 Actor：一次射线可以直接查询，但持续区域需要位置、生命周期、复制、Cue 和周期 Tick。统一 Agent 结构允许两者共用配置。

### 11.3 用户确认与网络输入

| 字段 | 含义 |
|---|---|
| `bUserConfirmInput` | 是否由玩家确认位置/目标 |
| `bServerWaitLocationInfo` | 服务器是否等待客户端位置数据 |
| `bUseClientCameraInfo` | 是否使用客户端相机方向 |
| `bPredictionDelayDamage` | 预测表现先行，伤害延迟到权威确认 |
| `bShowSync` | 是否显示/调试同步状态 |
| `bServerVerifyClientResult` | 服务器是否验证客户端候选结果 |

只有极少数 Scope 开 `bUseClientCameraInfo` 或 `bServerVerifyClientResult`。配置为 true 不等于信任客户端：协议代码仍需验证时间戳、最大距离、角度、起点和遮挡。

### 11.4 形状与朝向

| 字段 | 含义 |
|---|---|
| `TraceType` | Sphere/Cylinder/Box/Sector/Line/Capsule/Frustum |
| `Length` | 射线/长形检测长度 |
| `Radius` | 球/圆柱/胶囊半径 |
| `HalfHeight` | 胶囊/圆柱半高 |
| `BoxSize` | 盒体 X/Y/Z 尺寸 |
| `HorizontalAngleDegree` | 扇形水平角 |
| `VerticalAngleDegree` | 垂直角 |
| `bSectorPercentage` | 是否使用扇形百分比裁剪 |
| `SectorStart/EndPercentage` | 扇区起止比例 |
| `SectorRotationOffset` | 扇区旋转偏移 |
| `ShapeOffset` | 形状相对 Anchor 偏移 |
| `RotationType` | 从 X/Z 轴或自定义方向旋转 |
| `CheckDir` | 过滤/检查方向 |
| `AimDirType` | 使用 First 或 Final AimDir |

`ShapeParams_Enemy/Teammate/Scene` 可以为不同目标类别覆盖 TraceType 和尺寸。例如对敌人用更宽的辅助命中球，对场景仍用精确线，避免射击贴墙时不合理命中。

### 11.5 Anchor、起终点与 Trace 模式

| 字段 | 含义 |
|---|---|
| `AnchorData` | AnchorBone、AnchorOffset、AimOffset |
| `bCloseEvaluateTraceStart` | 是否关闭/改变起点求值 |
| `bFixTraceEndWhenOcclusion` | 遮挡时是否截断终点 |
| `TraceMode` | Single、Multi_Overlap、Multi_Sweep |
| `bMulti` | 是否返回多目标 |
| `ResultSortMode` | 按距离或角度排序 |
| `bShouldFixTraceHit` | 是否修正 HitResult |
| `bTraceSupplement` | 是否执行补充 Trace |
| `MaxTraceNumForOptimization` | 性能保护上限 |

`First` AimDir 通常指输入开始/原始瞄准方向，`Final` 可能是辅助瞄准或遮挡修正后的方向。确切算法属于项目代码，但配置区分两者可以避免所有技能被统一 AimAssist 改写。

### 11.6 传送门支持

| 字段 | 含义 |
|---|---|
| `bCanCrossPortal` | Trace 是否允许跨传送门继续 |
| `bPortalAsTraceResult` | Portal 本身是否作为一个结果返回 |

约 779/882 个已扫描 Scope 行允许跨门，说明传送门支持被下沉到检测基础设施，而非只写在奇异博士 Ability。实现需要把射线分段、变换剩余方向/距离、限制递归次数并合并排序后的命中结果。

### 11.7 Scene、遮挡与过滤

`SceneTraceType` 包含：是否检测场景/盾、形状、方向、平面、半径、Multi 修正等。

`Occlusion` 包含：

- 忽略所有/敌人/队友/门；
- 是否只对敌人检查 BlockVisibility；
- 自定义 ChannelPreset；
- 骨骼补充遮挡点；
- Offset、结束策略、Throwable Box Scale。

`TraceRule` 与 `TraceRequirements` 负责阵营和 Tag 过滤；`ExtendFilter` 可再按角度、方向与自定义方向过滤。

为什么过滤分三层：

1. TraceRule 决定物理查询谁；
2. TagRequirements 决定业务上谁有效；
3. Occlusion/Angle 决定空间关系是否成立。

### 11.8 对结果施加什么

| 字段 | 含义 |
|---|---|
| `BaseDamage` | 共享伤害结构 |
| `ImpulseLevelInfo/Filter/DirConfig` | 冲量等级、对象过滤和方向 |
| `ImpulseDirectionFixAngle` | 冲量方向修正角 |
| `ChaosFieldQuote` | 联动混沌/破坏场 Agent |
| `BeHitAnimConfigID` | 受击反应 |
| `BuffInfos` | Buff 应用、移除和唯一应用规则 |
| `BuffSpecs_ToSelf` | 对 Source/自身施加 Buff |
| `RemovalBuffIDs` | 命中时移除 Buff |
| `GameplayCues` | 命中/范围 Cue |
| `HitImpactCuePlayRule` | 命中 Cue 播放规则 |
| `bEnableRemoteClientCue` | 远端客户端是否播放 Cue |

`UniqueApplyRules` 提供唯一应用模式与“被移除后是否允许重施”。持续范围必须配置，否则每个 TracePeriod 都可能无限叠 Buff。

### 11.9 次数、频率与 Cost

| 字段 | 含义 |
|---|---|
| `MaxApplyTimes` | 对目标/总计的最大应用次数 |
| `bEndScopeWhenReachMaxApplyLimitation` | 达上限结束 Scope |
| `bIgnoreApplyInterval` | 忽略默认应用间隔 |
| `bCommitCostPerTrace` | 每次检测提交资源 |
| `bEndScopeWhenCostFailed` | 资源不足时停止 |
| `bSkipActionLogStatistics` | 不计入通常统计 |

### 11.10 高级/性能字段

`AdvanceParams` 可见：

- `bDedupOnAbilityHits`；
- Tick Trace 合并与间隔；
- `bMergable`；
- `bSelfIgnoreTrace`；
- 服务器回滚、RollbackIntent；
- Trace/FixTrace Accelerator。

这些字段选择性能/补偿策略。真正的批处理、历史帧缓存和回滚查询必须由 C++ 管线实现。

### 11.11 配置示例

一个持续治疗圈可以这样配：

1. TraceType=Sphere，Radius=目标半径，Multi_Overlap。
2. ScopeAgent.TraceDelay=0，TracePeriod=0.5，LifeTime=6。
3. TraceRule 只允许 Self/Teammate，忽略 Enemy。
4. BuffInfos 引用治疗 BuffSpec，UniqueApplyRule 避免同 Tick 重复。
5. BuffSpecs_ToSelf 可加施法者状态。
6. GameplayCue 配范围常驻与治疗命中表现。
7. 服务器执行治疗，客户端只预测圈的放置和视觉。

## 14. `FMarvelSummonerAgentTableRow`：召唤物

## 17. `AeroConfigCommonItem`：飞行状态配置

### 17.1 结构

| 字段 | 含义 |
|---|---|
| `FlyModeID` | 飞行模式 ID |
| `AeroState` | 对应状态枚举 |
| `AeroConfig` | 具体运动/输入参数；可为 null |
| `Delivery` | 发布标记 |

`AeroConfig` 观察字段：

- `bEnable`、`bOpenCtrl`、`bOpenCamera`；
- W/A/S/D/Space 输入开关；
- 是否能水平/垂直移动；
- 最大水平/垂直速度、加速度、减速度；
- 垂直方向切换加速度；
- 地面悬浮、最低下降/悬浮高度；
- GroundTraceContext；
- 是否启用 Buff 效果。

### 17.2 为什么 FlyMode 独立于 Ability

钢铁侠常驻飞行、奇异博士短时悬浮、万磁王被动漂浮可能复用同一 MovementComponent，但输入、加速度、镜头和地面限制不同。Ability 只切换 FlyMode 并管理 Cost/持续时间，MovementComponent 根据 FlyConfig 执行网络移动。

配置不能直接实现飞行网络预测。需要自定义 CharacterMovementMode、SavedMove/MoveData、服务器校正和动画状态。

## 18. `GameplayCueOptimizationCommonItem`：Cue 优化配置

### 18.1 字段

| `bEnableOptimization` | 是否启用优化 |
| `bCustomOptimizationContext` | 是否使用自定义 Context |
| `Context` | 距离、视锥、屏幕尺寸、执行端和各表现类型开关 |

## 20. `MarvelHeroBaseAttributeTable`：英雄基础 Attribute

### 20.1 主结构

| 字段 | 含义 |
|---|---|
| `HeroId` | 英雄 ID |
| `TName` / `EnName` | 中英文名 |
| `AttrSpecs` | 一个或多个形态的属性规格 |
| `ExtendedConfig` | 英雄独有基础属性扩展 |
| `AmmoIDs` | 初始/关联弹药资源 ID |
| `Delivery` | 发布标记 |

### 20.2 `AttrSpec`

观察到的通用字段：

- `TypeTag`：形态 Tag；
- `TurnSpeed`；
- `MoveSpeed`、`MoveBackSpeedRatio`；
- `MaxHealth`；
- `Shield`、`MaxShield`；
- `ShieldRegenRecover`、`ShieldRecoverDuration`；
- `Armor`、`MaxArmor`；
- `MoreAttributes`；

这些数组承载并非每个英雄都有的 Attribute/资源，例如怒气、特殊护盾、连击值。复刻时应使用 GameplayTag/GameplayAttribute 引用与初始值，而不是给基础行持续增加 `HeroXEnergy` 列。

基础值应由服务器通过初始化 GE 或 `InitStats`/AttributeSet 初始化。客户端表只用于 UI 预览，不能决定权威 MaxHealth。

## 21. Camera、Curve、Cue 与实体蓝图资源

这些不是 DataTable 行，但构成配置引用图的一部分。

### 21.1 `CameraInterp`

全量导出中大量 CameraInterp 资产包含：

- FOV 目标、插值和恢复速度；
- SpringArm 长度、SocketOffset；
- CameraLag 速度和最大距离；
- Transcomposer/DeadZone；
- 相对角色或世界空间；
- CameraCurve；
- 优先级。

为什么独立资产：冲刺、瞄准、飞行可复用相同镜头策略；多个镜头效果还需要按优先级混合和恢复。AbilityItem/Timeline 只引用资产并选择激活时机。

### 21.2 CameraShake

FModel 可见 LegacyCameraShakePattern 和大量技能专用 Shake 类。配置振幅、频率、持续与衰减；播放端由 AbilityItem 或 Timeline 节点决定。命中敌方的 Shake 和自身施法 Shake 必须分开，避免远端玩家收到错误镜头事件。

### 21.3 CurveFloat

约数百条 CurveFloat 用于：

- 伤害/距离衰减；
- Dash 速度；
- Projectile 重力、速度、半径；
- 镜头插值；
- 后坐力/冲量；
- 资源或尺寸随时间变化。

曲线的 X 轴单位必须在字段 Tooltip 中声明：秒、距离、百分比还是归一化 0..1。否则同一条曲线被不同模块误读。

### 21.4 Cue 蓝图

Cue 资产通常带 Niagara、Audio、Decal、Mesh、CueDataManagerComponent 和项目组件。Buff/Scope/Projectile 只保存 CueTag，GameplayCueManager 根据 Tag 找到实现。

配置要求：

- Execute、OnActive、WhileActive、Removed 生命周期匹配；
- 持续 Cue 必须能被预测拒绝和 EndAbility 清理；
- 参数从 `FGameplayCueParameters` 或 TypedCue 数据读取；
- 不在 Cue 中造成权威伤害；
- 与 CueOptTable 的距离/视锥/音频策略一致。

### 21.5 Projectile/Summoned/Ammo 蓝图

这些 Actor 蓝图常导出：Root、Collision、Movement、Audio、ActorPoolComponent、ASC、AIController 或自定义组件。表中的 Agent 字段选类和参数，蓝图组件实现能力。

判断边界：

- 半径、速度、资源引用、Tag 规则放表；
- Tick、Sweep、Homing、网络复制、对象池回调放 C++/组件；
- 特殊 Hero 逻辑放专用 Component，不放 Level Blueprint。

## 22. Common、Hero、Level、Activity 与 GameMode 配置层

### 22.1 数据层级

解包目录中可见：

```text
AbilitySystem/Common/...
AbilitySystem/<HeroId>/...
AbilitySystem/Level/...
AbilitySystem/Activity/...
AbilitySystem/GameMode/...
Data/DataTable/GameMode/...
```

合理的解析顺序是：

```text
Common 默认
  -> Hero 基础
  -> Level/GameMode 规则
  -> Activity/赛季玩法覆盖
  -> 运行时 Effector/热更
```

### 22.2 Primary 表

目录中还能看到 `PrimaryAbilityTable`、`PrimaryBuffSpecTable`、`PrimaryScopeAgentTable`、`PrimaryProjectileAgentTable` 等。它们通常服务关卡主能力、玩法或一套优先数据域。不要仅凭文件名假定它一定覆盖普通英雄表，应读取 Composite ParentTables 的实际顺序。

### 22.3 Copy 与玩法表

`CopyAbilityTable`、Avengers、2206/2207/2208、活动 10120/10130 等表复用同一 RowStruct。说明玩法扩展主要通过新增同构行和 Composite 聚合完成，而不是为每个玩法复制整个战斗系统。

### 22.4 HotFix 表

当前导出的 `MarvelBuffRuleHotFixTable`、`MarvelControlHotFixTable` 行为空，但 RowStruct 存在，说明项目预留了运行时/版本修正规则。空表不能证明系统未使用，可能由服务器或其他包填充。

复刻热更必须限制：

- 只允许白名单字段；
- 带版本、适用模式和生效时间；
- 服务器与客户端数据哈希可核对；
- 旧回放能找到当时版本；
- 修改网络协议/类布局必须发客户端版本，不能靠表热更。

## 23. 从零配置一个技能的标准流程

### 23.1 第一步：决定使用哪个模板

先判断它是：

- 瞬时枪线；
- 投射物；
- 持续/瞬时 Scope；
- 召唤；
- 跳跃/飞行/Dash；
- Buff/被动；
- 选择/放置；
- 独特机制。

能用模板就不要新建专用 Ability 基类。独特机制也应尽量复用 Scope、Projectile、Buff 和 Timeline 节点。

### 23.2 第二步：创建战斗原语

根据需要创建：

1. EffectTemplate：如果出现一种新的共性状态语义；
2. GameplayEffect：把模板映射到 GAS；
3. BuffSpec：具体数值、Duration、叠层；
4. Scope：形状、过滤、伤害/Buff；
5. Projectile：运动、碰撞、命中 Quote；
6. Summoner：Actor、属性、数量和网络；
7. Equipment/InstantAmmo：若技能属于武器。

不要每个技能都新建 EffectTemplate。只改数值/持续时间时复用模板，新建 BuffSpec。

### 23.3 第三步：创建 Timeline

划分：

```text
Active/前摇 -> Missile/出手 -> Break/后摇 -> End
```

在轨道添加 SpawnScope/Projectile/Summoner、ApplyBuff、Tag、Camera/Cue 节点。确保服务器逻辑节点在 Dedicated Server 可运行，视觉节点有本地限制。

### 23.4 第四步：创建 ExtendConfig

选择已有 Config ScriptStruct/DataAsset，填写 ID、速度、半径、曲线等。如果必须新增结构：

- 先确认不是已有公共子结构；
- 字段提供单位、范围和默认值；
- 只保存静态参数，不保存运行时 Handle/Timer；
- 给模板注册配置类型校验器。

### 23.5 第五步：创建 Ability BP

配置：

- AbilityTags；
- Activation Owned/Required/Blocked；
- Block/Cancel 关系；
- NetExecutionPolicy 与 InstancingPolicy；
- 阶段取消窗口；
- 必要的专用 Task 编排。

Ability BP 不直接硬编码 DataTable 路径；从当前 AbilityItem/ResolvedConfig 取得引用。

### 23.6 第六步：创建 MarvelAbilityItem

关联 GrantedAbility、ExtendConfig、Timeline、InputAction、Cost/CD 阶段、Combo、Cue、Camera 和命中反馈。

配置问题清单：

- 按下、松开、长按、确认、取消各是什么输入；
- Cost 在检查、预留、提交哪个阶段；
- 取消/未命中/死亡时是否进 CD；
- 哪些表现预测，拒绝时如何移除；
- Timeline 结束是否一定 EndAbility；
- 是否存在循环但没有退出条件。

### 23.7 第七步：添加 AbilityTable 行

填写 AbilityID、名字、CD/Charge、UI、日志、AbilityAsset，并加入英雄/玩法子表。Composite 表中验证 ID 唯一或覆盖来源明确。

### 23.8 第八步：授予与输入

生成管线根据 Hero/Mode 解析 AbilityTable，在服务器 `GiveAbility`。客户端从 AbilityItem 的 InputAction/语义 InputBind 绑定输入。被动可在授予后按配置自动激活。

## 24. 四个典型配置配方

### 24.1 连发步枪

```text
AbilityTable
  -> AbilityItem(PrimaryAttack, CostStage=Missile)
  -> Config_105(EquipID, FireModeIndexes, RoundRobin)
  -> Weapon.ShootingLogic_Instant
  -> InstantAmmo(BaseDamage, Range, TraceRule, Cue)
  -> Ability BP(LocalPredicted, Attack Tags)
```

需要代码：射击时钟、确定性散布、客户端输入批处理、服务器历史命中验证、伤害 Execution。

### 24.2 榴弹

```text
Timeline Missile
  -> SpawnProjectile(ProjectileID)
  -> ProjectileAgent(Gravity, Collision, Penetrate/Bounce)
  -> ScopeQuote on hit
  -> Explosion Scope(Sphere, Damage, Buff, Cue)
```

配置负责速度、半径、伤害与 Cue；代码负责运动、Sweep、预测替身和服务器命中。

### 24.3 控制 Buff

```text
EffectTemplate(Type=Negative/Special, StatusTags, Dispel, Stack)
  -> GE Components(TargetTags, Requirements, Immunity, Cancel/Block)
  -> BuffSpec(Duration, Magnitude, Cue, Source stacking)
  -> Scope/Projectile BuffApplyInfo
```

代码负责韧性、服务器 CanApply、CDR 系统响应 Tag；配置不直接禁用 CharacterMovement。

### 24.4 可放置召唤物

```text
AbilityItem(BindInputs Confirm/Cancel)
  -> ExtendConfig(placement Trace, SummonerID)
  -> Timeline SpawnSummoner
  -> SummonerAgent(Actor, ASC, AttrSpec, QuantityGroup)
  -> Summoned AbilityQuote
  -> Scope/Projectile for autonomous attacks
```

代码负责放置合法性、生成管线、网络所有权、数量管理和预测对象配对。

## 25. 配置与代码的边界

| 配置负责 | 代码负责 |
|---|---|
| 选择 Ability/Actor/Component/Curve/Cue | 类的实际算法与生命周期 |
| ID、Tag、TagQuery、阵营规则 | Tag 关系执行和冲突确定性 |
| 数值、时长、频率、半径、速度 | 权威计算顺序、钳制、反作弊 |
| Trace/Collision 策略参数 | 物理查询、Portal 分段、历史回滚 |
| 弹跳/穿透开关和次数 | 轨迹重建、去重、网络同步 |
| 预测开关与容差 | PredictionKey 协议、拒绝/追帧清理 |
| 数量限制和替换策略 | 并发安全的实体管理器 |
| Cue 资产和优化阈值 | Cue 池、去重、执行端和 Niagara DI |
| 模式覆盖值 | 合并算法、版本、审计与缓存 |

一个字段只有在“代码已经实现了稳定语义”后才有意义。`bCanCrossPortal=true` 不会自动产生传送门能力；它只是允许检测管线走已经实现的 Portal 分支。

## 26. 必须做的配置校验

### 26.1 ID 与引用

- AbilityID/BuffID/ScopeID/ProjectileID/SummonerID 全局或数据域内唯一；
- ID 前缀与所属 Hero 不一致时给警告，但不依赖前缀运行；
- 所有 Quote、Timeline 节点和 ExtendConfig 引用存在；
- ObjectPath 能被 AssetManager/Cook 收集；
- Composite 重复 Row 输出覆盖链。

### 26.2 Ability

- AbilityItem 有 GrantedAbility；
- Config 类型与 Ability 模板匹配；
- Timeline 逻辑上存在结束路径；
- 循环 Ability 有取消、资源耗尽或超时条件；
- Cost/CD 阶段存在于 Timeline；
- Tag Block/Cancel 不产生永久互锁；
- NetExecutionPolicy 与行为匹配。

### 26.3 Buff/Effect

- EffectID 存在且 GE 类型匹配 DurationPolicy；
- SetByCaller Tag 完整；
- StackLimit、Overflow、Expiration 组合合法；
- Begin/End/Break Buff 链无环；
- Instant Effect 不配置无意义 Period；
- 硬控有免疫/韧性类别；
- 预测 Buff 可完整回滚。

### 26.4 Scope

- 形状参数非负，Sector 角度/百分比合法；
- TracePeriod 为 0 时不会创建无限 Tick；
- Multi + 无上限有候选数预算；
- 持续 Scope 有唯一应用/间隔规则；
- ClientResult 开启时同时有服务器验证策略；
- Portal 最大递归和总距离受限。

### 26.5 Projectile

- LifeTime、MaxDistance 至少一个有效；
- Bounce/Penetrate 次数有上限；
- ActorReplicationDisabled 时有自定义同步路径；
- Virtual/Swift 类型具有对应管理器；
- ClientResult/BatchRPC 的协议版本一致；
- 命中 Quote 不形成 Projectile -> Scope -> Projectile 无限环。

### 26.6 Summoner

- bNeedASC=true 时 AttrSpec/ASC 类有效；
- MaxNum 与 QuantityStrategy 合理；
- Replace 策略不会删除权威任务仍引用的实体；
- bSupportRollback=true 时 Actor 支持预测清理和匹配；
- AlwaysRelevant 仅用于极少数关键实体；
- AI/AbilityQuote 不会在客户端重复激活。

### 26.7 表现与性能

- Dedicated Server 不加载 Camera/Niagara/纯音频；
- 持续 Cue 必有 Remove；
- CueOpt 的距离、屏幕尺寸和音频半径合理；
- Scope 每秒 Trace 数、Projectile 数、Summoned 数有预算；
- 对象池回收前解除 ASC、Delegate、Timer 和 Attachment。

## 27. 推荐的复刻数据结构

不需要照抄商业项目类名，但应保留职责分层：

```cpp
USTRUCT(BlueprintType)
struct FAbilityTableRow : public FTableRowBase
{
    GENERATED_BODY()
    FAbilityId Id;
    FHeroId HeroId;
    float BaseCooldown = 0.f;
    int32 CooldownGroup = 0;
    TSoftObjectPtr<class UAbilityDefinition> Definition;
};

UCLASS(BlueprintType)
class UAbilityDefinition : public UPrimaryDataAsset
{
    GENERATED_BODY()
public:
    TSoftClassPtr<UGameplayAbility> GrantedAbility;
    FAbilityInputConfig Input;
    FAbilityCostConfig Cost;
    TArray<FCombatTimelineBinding> Timelines;
    FInstancedStruct ExtendConfig;
    FAbilityPresentationConfig Presentation;
};
```

战斗原语使用强类型 ID：

```cpp
FAbilityId
FBuffSpecId
FEffectTemplateId
FScopeId
FProjectileId
FSummonerId
FEquipmentId
FInstantAmmoId
FFlyModeId
```

数据访问统一走 Repository：

```cpp
const FResolvedBuffSpec& ResolveBuff(FBuffSpecId Id, const FCombatDataContext& Ctx);
const FResolvedScopeSpec& ResolveScope(FScopeId Id, const FCombatDataContext& Ctx);
```

业务代码不要直接 `FindRow`，否则玩法覆盖、热更、缓存、溯源和版本无法统一。

## 29. 结论

《漫威争锋》的配置系统不是“数据驱动取代代码”，而是把战斗拆成少量稳定原语：Ability、Timeline、Effect/Buff、Scope、Projectile、Summoner、Weapon、Cue。代码实现每种原语的算法、网络和生命周期；配置用 ID、Tag、曲线和资产引用把它们组合成英雄技能。

理解每项配置时始终问四个问题：

1. **它是谁？** ID、Tag、所属数据域。
2. **它引用谁？** Ability、Buff、Agent、Timeline、Curve、Cue。
3. **它何时执行？** Ability 阶段、Timeline 时间、Period、生命周期绑定。
4. **谁有权执行？** 本地预测、服务器权威、远端表现、Dedicated Server。

只要这四个答案明确，配置就能被验证、覆盖、调试和复用；如果一个 Config 同时藏着运行时状态、网络协议和任意脚本逻辑，它就已经越过了配置应有的边界。
