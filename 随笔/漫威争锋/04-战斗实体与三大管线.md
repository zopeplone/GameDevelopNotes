# 04 战斗实体与三大管线

## 1. 为什么 Ability 不直接做命中

英雄技能差异再大，最终仍反复使用三类战斗实体：

- Projectile：有飞行时间和轨迹的投射物。
- Field/Scope：瞬时或持续的空间检测。
- Summon：具有属性、技能、AI 或独立生命周期的召唤物。

如果每个 Ability 自己写 Trace、Spawn、阵营、遮挡和网络验证，传送门、反弹、吸收、召唤物转发等跨英雄机制会要求修改所有技能。管线化的目标是让 Ability 只声明“我要哪种检测/实体”，执行细节由统一系统处理。

## 2. 检测管线：ScopeAgentTable

### 2.1 四层配置

```text
全局/玩法规则
  -> Source（Scope/Projectile/Ammo 的检测意图）
  -> Target（角色/召唤物/场景的被检测规则）
  -> 通用规则（阵营、形状、角度、距离、遮挡、Tag）
```

### 2.2 身份与形状

| 字段组 | 代表字段 |
|---|---|
| 身份 | `Id`、`HeroName`、`Desc`、`AssetTags` |
| 形状 | `TraceType`、`Radius`、`Length`、`HalfHeight`、`BoxSize` |
| 扇形 | `HorizontalAngleDegree`、`VerticalAngleDegree`、`SectorStartPercentage` |
| 位置旋转 | `AnchorData`、`ShapeOffset`、`RotationType`、`CheckDir` |
| 多目标 | `bMulti`、`MaxTraceNumForOptimization`、`ResultSortMode` |

形状参数必须互斥校验。例如 Sphere 不应同时要求 BoxSize；Sector 的角度必须在合法范围；Length 为 0 的射线要构建失败。

### 2.3 目标与过滤

- `TraceRequirements`：来源/目标的通用 Tag 条件。
- `ShapeParams_Enemy` / `Teammate` / `Scene`：按对象类型定制形状或开关。
- `ExtendFilter`：业务过滤器。
- `UniqueApplyRules`：同一对象/组件/角色的去重规则。
- `CollisionTagRequirements`：碰撞对象状态条件。
- `SceneTraceType`：场景检测策略。

先进行廉价过滤：阵营、对象类型、Tag；再做距离、角度、遮挡；最后执行昂贵业务规则。这样可以把高频 Scope 的成本限制在候选集上。

### 2.4 遮挡与传送门

当前 Scope 字段直接包含：

- `Occlusion`
- `bCanCrossPortal`
- `bPortalAsTraceResult`
- `bFixTraceEndWhenOcclusion`
- `bUseSpecialTraceShape_Scene/Teammate`

传送门不能在 Ability 层“特殊处理一次 Trace”。统一检测管线需要支持分段射线：

```text
Start -> Portal A
Transform position/direction
Portal B -> original remaining distance
merge result while preserving source, team and hit order
```

并设置最大穿门次数，防止成对传送门形成无限递归。

### 2.5 应用结果

- `BaseDamage`：基础伤害输入，不是最终伤害。
- `BuffInfos` / `BuffSpecs_ToSelf`：对目标/自身施加 Buff。
- `RemovalBuffIDs`：命中时移除状态。
- `GameplayCues`：命中表现。
- `Impulse*`：冲量。
- `ScopeQuote` / `ChaosFieldQuote`：组合其他战斗实体或场机制。

一次检测应产生标准 Result：目标 Actor、命中组件、位置、法线、距离、阵营快照、Source/Instigator、PredictionKey。后续伤害、Buff、Cue 都消费同一 Result，避免各模块重新 Trace。

### 2.6 客户端与服务器

| 字段 | 意图 |
|---|---|
| `bUseClientCameraInfo` | 瞄准起点使用客户端相机信息 |
| `bServerVerifyClientResult` | 服务器复核客户端命中 |
| `bServerWaitLocationInfo` | 服务器等待客户端目标数据 |
| `bPredictionDelayDamage` | 表现先行，伤害延后到权威结果 |
| `bEnableRemoteClientCue` | 远端表现事件 |

客户端可以预测准星、动画和本地弹道，但最终目标集必须由服务器验证。验证容差要考虑 RTT、角色历史位置与弹道半径，不能简单重跑当前帧 Trace。

## 3. ProjectileAgentTable：延迟弹道

### 3.1 核心配置

| 领域 | 字段 |
|---|---|
| 类与运动 | `ProjectileAgent`、`AdvanceParams`、`AimDirType`、`bAlternateMovement` |
| 碰撞 | `CollisionRule`、`CollisionTagRequirements`、`bUseTraceVerify` |
| 伤害 | `BaseDamage`、`BuffSpecs`、`BuffSpecs_ToSelf` |
| 反弹 | `bShouldBounce`、`BounceRule`、`Bounciness`、`BoundCountMax` |
| 穿透 | `bShouldPenetrate`、`PenetrateRule`、`PenetrateCountMax`、衰减曲线 |
| 引用 | `ScopeQuote`、`SummonerQuote`、`ChaosFieldQuote` |
| 网络 | ClientResult、BatchRPC、Swift/VirtualProjectile、同步相关性 |
| 性能 | `PreCreateCount`、`bOpenCache`、UpdateRate、VisibilityBasedUpdateType |

### 3.2 反弹与阵营转换

美国队长盾牌反弹要求标准 Projectile Context 可变更：

- Source/Instigator；
- Team/Camp；
- 飞行方向和剩余寿命；
- 已命中集合；
- 伤害归因与击杀归属；
- Cue 参数。

反弹不是只改 Velocity。若阵营和 Source 不换，后续过滤、伤害、统计与网络表现都会错误。

### 3.3 穿透

每次穿透更新：

- 剩余穿透次数；
- 已命中对象去重；
- `PenetrateDamageFalloffCurve` 与 Floor；
- 剩余最大距离；
- 是否继续应用 Buff/Quote；
- RPC 批处理窗口。

不要用 Projectile Tick 直接重复 ApplyDamage；碰撞结果应进入统一战斗数据管线。

### 3.4 Swift 与 Virtual Projectile

解包字段表明系统包含 Swift、Virtual、批量 RPC、并行运动、按可见性降频等优化路径。建议阈值：

- 玩家需要观察并交互：真实复制 Actor。
- 高速短命且只需要命中结果：Swift/服务器容器。
- 纯数学轨迹、数量巨大：Virtual Projectile。
- 远端不可见：降低更新率，但服务器碰撞精度不能随渲染可见性变化。

## 4. InstantAmmoTable：瞬时弹道

瞬时弹道适合枪线、激光和无可观察飞行时间的攻击。

关键字段：

- `AmmoClass`、`AmmoID`、`AmmoFireRange`、`AmmoTraceRule`；
- `RadiusForEnemy/Ally/Scene`；
- `bShouldPenetrate`、`PenetrateCount/Distance/DamageCurve`；
- `BuffSpecs`、`BuffSpecs_ToSelf`、`GameplayCues`；
- `BaseDamage`、`DestructibleDamage`；
- `TraceRequirements`。

与 Projectile 的边界：玩家是否有时间观察、拦截、反弹或传送该实体。万磁王磁场要同时接管 Projectile 和 InstantAmmo 的检测路径，否则只能吸收“看得见的子弹”。

## 5. SummonerAgentTable：召唤物

### 5.1 何时使用 Summon

具备下列任意两项就应考虑 Summon，而不是单纯 Niagara：

- 有生命/属性；
- 可被检测和受击；
- 自己释放技能；
- 有 AI；
- 需要阵营、网络相关性或击杀统计；
- 生命周期超过一个瞬时技能阶段。

### 5.2 字段组

| 领域 | 字段 |
|---|---|
| 类与属性 | `SummonerAgent`、`AttrSpec`、`bNeedASC`、`bNeedBuff` |
| 数量 | `MaxNum`、`QuantityGroupID`、QuantityLimitStrategy |
| 初始化 | `InitBuffIDs`、`AbilityQuote`、`ScopeQuote` |
| 阵营过滤 | Self/Teammate/EnemyTagRequirements |
| 统计 | DamageToInstigatorEnergy、DamageToOwnerEnergy、KillTips |
| 网络 | AlwaysRelevant、OwnerRelevancy、ActiveGE/PredictionKeyMap 复制开关 |
| 预测 | `bSupportRollback`、`PredictGameplayCues` |
| 表现 | Dithering、Stencil、VisibleType、GameplayCues |

`bNeedASC` 应只为真正需要 Ability/Effect 的召唤物开启。大量一次性实体各带完整 ASC 会造成 ActiveGE、Tag 和复制成本。

### 5.3 生命周期

召唤物需要明确：

- 谁拥有它；
- Owner 死亡、换英雄、离开对局时是否销毁；
- 到达数量上限时替换最旧、拒绝还是销毁最远；
- Ability 预测失败时是否可回滚；
- 服务器销毁与客户端淡出谁先执行。

## 6. EquipmentTable 与 FlyConfigTable

### 6.1 Equipment

EquipmentTable 把“武器持有状态”从攻击 Ability 中独立出来：

- WeaponClasses、AmmoSpec；
- 初始装备、切换、自动换弹；
- 武器 Owned Tags；
- 手部 IK、Socket 和左右手权重；
- UI、准星散布等级；
- 多持和弱持有模式。

惩罚者同时存在步枪、霰弹枪、手枪、炮台等 Equipment/Weapon 资产。切武器 Ability 应只改变装备状态和 Tag，射击 Ability 根据当前装备读取 AmmoSpec。

### 6.2 FlyConfig

FlyConfigTable 只有 `FlyModeID`、`AeroState`、`AeroConfig`、`Delivery`，说明详细参数被封装在 AeroConfig 内。飞行状态至少要覆盖：

- 进入/退出；
- 上升/下降输入；
- 转向和最大速度；
- 重力与落地恢复；
- 被控制/死亡/换形态的强制退出；
- 预测与服务器位置纠正。

## 7. 生成管线

英雄生成不是一次 SpawnActor，而是配置重建：

```text
选择 HeroID / Skin / Mode
  -> 合并 HeroTable 与 BaseAttributeTable
  -> 创建 Pawn / PlayerState / ASC 的 Owner-Avatar 关系
  -> 初始化 AttributeSet
  -> 加载 AbilityTable 并 GiveAbility
  -> 初始化 Equipment / Ammo / Fly / 默认 Buff
  -> 应用模式效果器和禁用规则
  -> 建立 UI、输入、Cue 与统计上下文
```

ASC 初始化必须在 OwnerActor、AvatarActor 都有效后调用；换形态或换 Pawn 时重新绑定 Avatar，但稳定的 CD/Ability 需要放在不会随 Pawn 销毁的 Owner（常见为 PlayerState）上。

## 8. 战斗数据管线与效果器

效果器是对数据读取的拦截器，而不是偷偷修改 DataTable：

```text
GetValue(Hero=1034, Ability=103431, Field=AbilityCD)
  -> Base value
  -> GameMode modifiers
  -> Equipment/Talent modifiers
  -> Temporary match rules
  -> final value + provenance
```

每次覆盖记录：来源资产、优先级、操作类型（Add/Multiply/Override）、旧值、新值。数值字段允许组合运算；类引用、Tag 集合和布尔值通常只允许 Replace/Merge 等受限操作。

## 9. 管线验收

- [ ] Source、Target、全局规则可以分别配置。
- [ ] 所有检测输出统一 Result/Context。
- [ ] 传送门支持分段检测并限制递归次数。
- [ ] 反弹同时更新方向、阵营、来源和归因。
- [ ] Projectile、InstantAmmo 都接入拦截/吸收协议。
- [ ] Summon 数量、所有者、死亡和预测生命周期明确。
- [ ] 可视性优化不改变服务器判定。
- [ ] 模式差异通过数据视图覆盖，不复制基础技能。
- [ ] 每个覆盖值可追溯来源。
