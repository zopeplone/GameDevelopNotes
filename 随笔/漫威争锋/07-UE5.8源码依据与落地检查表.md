## 2. GameplayAbility 为什么这样配

### 2.1 Commit 与 End 是硬生命周期

`Public/Abilities/GameplayAbility.h`：

- 115：注释要求 ActivateAbility 调用 CommitAbility。
- 119：注释要求 Ability 最终调用 EndAbility。
- 313-338：CommitAbility、CommitCooldown、CommitCost API。
- 556-560：蓝图 Activate 图必须 Commit 与 End。
- 586-604：EndAbility API。

因此：

- Cost/CD 不能散落在 Timeline Notify 和输入回调里。
- 每条成功、失败、取消路径都必须汇合到 EndAbility。
- MarvelAbilityItem 的死亡中断、资源耗尽、用户取消字段必须最终驱动同一生命周期。

### 2.2 标签关系是 GAS 原生协议

同一文件：

- 475-476：AbilityTags。
- 739：CancelAbilitiesWithTag。
- 743：BlockAbilitiesWithTag。
- 747：ActivationOwnedTags。
- 751：ActivationRequiredTags。
- 755：ActivationBlockedTags。

所以 Marvel 的 AbilityPriority 关系层使用 GameplayTag 是顺着 GAS 的执行模型，而不是额外维护一套互不相通的枚举。

### 2.3 Cost/CD 应使用 GameplayEffect

- 723：CostGameplayEffectClass。
- 731：CooldownGameplayEffectClass。

Cooldown Effect 能自然提供 ActiveGE 时长、Tag 查询、复制和预测合并。UI 应查询 ASC/Effect，而不是独立倒计时。

### 2.4 Instancing 与网络

- 74：有状态/事件复制的 Ability 必须实例化。
- 689-715：ReplicationPolicy、InstancingPolicy、NetExecutionPolicy。

只要 Ability 拥有 Timeline Task、输入回调或成员状态，就必须审查 InstancingPolicy。LocalPredicted 决定在哪里执行，ReplicationPolicy 决定 Ability 实例状态是否复制，两者不是同一开关。

- 输入确认、释放和目标数据不应自建随意 RPC。

## 4. GameplayEffect 为什么分模板与实例

`Public/GameplayEffect.h`：

- 37：周期 Effect 在每个 Period 执行。
- 254-389：SetByCaller 数据与 Magnitude 计算。
- 560-597：FGameplayModifierInfo。
- 1043-1123：Spec 的 SetByCaller 复制、合并、设置与读取。
- 1087-1088：Instant Effect 强制没有 Period。
- 2103：GameplayEffect 的定义是修改 Attribute 与 Tag。
- 2256-2268：DurationPolicy、DurationMagnitude、Period。
- 2280-2284：Modifiers 与 Executions。
- 2301-2332：Overflow 与 GameplayCues。
- 2407-2436：StackingType、StackLimit、刷新和周期策略。
- 2466-2513：GEComponents 的组合、查询与创建。

对应 Marvel 资产：

- Effect 模板把 Duration 和 AttributeValue 做成 SetByCaller。
- BuffSpec 用 EffectID 选算法，用 AttributeValue/Duration 实例化 Spec。
- BuffSpec 的叠层 Override 对应 UE Stacking 字段。
- Effect_NNNN 中的 GEComponents 与 UE 5.8 组件模型一致。

## 5. GEComponent 为什么优于巨型子类

目录 `Public/GameplayEffectComponents` 包含：

- TargetTags
- TargetTagRequirements
- RemoveOtherGameplayEffect
- Immunity
- CustomCanApply
- ChanceToApply
- CancelAbilityTags
- BlockAbilityTags
- AssetTags
- AdditionalEffects
- Abilities

Marvel 的 Effect 资产组合这些组件，并增加业务组件。每个组件只负责一个生命周期钩子，能独立验证数据，避免所有 Effect 子类复制同一套 Apply/Remove 逻辑。

实现新状态时先问：

1. 是 Modifier/Execution 能表达吗？
2. 是已有 GEComponent 能表达吗？
3. 是否应新增可复用 Component？
4. 只有完整生命周期都独特时才建专用 GameplayEffect 子类。

## 6. AbilityTask 为什么适合技能模板

`Public/Abilities/Tasks/AbilityTask.h`：

- 24：建议参考 WaitOverlap 和 WaitTargetData。
- 43：OnDestroy 要注销回调。
- 74：Task 的 Waiting 状态模型。
- 124-125：Task 可获取 ActivationPredictionKey。
- 136：NewAbilityTask。

`AbilityTask_WaitTargetData.h`：

- 29-32：ValidData 与 Cancelled 输出。
- 48-52：创建或复用 TargetActor。
- 76：OnDestroy。

`AbilityTask_PlayMontageAndWait.h`：

- 64-78：创建 Task 并在 OnDestroy 清理。

因此 Timeline、Scope、Montage、输入都应通过 Task 形成可取消的异步单元。Ability End 会成为统一清理边界。

## 7. PredictionKey 为什么必须贯穿副作用

`Public/GameplayPrediction.h` 的说明是本项目预测设计的直接依据：

- 64-70：Key 的唯一标识和只回传原客户端规则。
- 83-92：客户端激活、服务器接受/拒绝、CaughtUp 流程。
- 95-112：GameplayEffect 和 GameplayCue 预测。
- 175-182：触发链使用 Base Key 和依赖关系。
- 192-208：Ability 内额外 ScopedPredictionWindow。
- 296-328：FPredictionKey 与拒绝/追上 Delegate。
- 435-465：DelegateMap、Reject、CatchUp、Dependency。
- 479-497：FScopedPredictionWindow。

结论：

- 预测不是“客户端先播动画”一个开关，而是每个副作用都绑定 Key。
- Ability 激活后每个新的输入原子动作都需要新的 Scoped Key。
- BuffSpec 的预测生成/删除、召唤物回滚、Projectile 代理和 Cue 去重必须共享同一 Key 链。

## 8. GameplayCue 为什么必须与逻辑分离

`Public/GameplayCueManager.h`：

- 128-141：Cue Manager 分发 Executed、Added、WhileActive。
- 170-180：Handle 与 Route GameplayCue。
- 187-196：Ability 使用复制 Cue，动画使用非复制 Cue的说明与 API。
- 228-241：Runtime 与 Editor 两套 Cue Object Library。
- 381-404：异步加载、缺失 Cue 和 RPC 数量检查。

`Public/GameplayCueInterface.h`：

- 23-46：Actor 接收 Cue 的接口。
- 92-98：Ability 可不经过 Effect 直接复制 Cue。
- 101-144：ActiveGameplayCue 使用 FastArray，支持预测移除。

因此：

- Cue 加载失败不能影响伤害和状态。
- Ability Timeline 的表现 Notify 可发 Cue，但不能反过来把 Niagara 当权威逻辑。
- CueOptTable、TypedCue 和对象池是表现层扩展，不改变 GAS 逻辑协议。

## 9. 从零搭建的模块顺序

### 阶段一：GAS 底座

1. 定义 ASC Owner/Avatar 策略和复制模式。
2. 定义 AttributeSet、伤害 Execution 与 EffectContext。
3. 建立 GameplayTag 词典和 Redirect 流程。
4. 实现 AbilitySet 授予与回收。
5. 建立统一的预测与 TargetData 规范。

### 阶段二：配置资产

1. AbilityTable 行结构。
2. MarvelAbilityItem 通用资产。
3. ExtendConfigInline 多态配置。
4. Effect 模板库。
5. BuffSpec 表和数据校验。
6. Timeline 与 Cue 资产。

### 阶段三：战斗实体

1. 标准 CombatContext/Result。
2. Scope 检测管线。
3. InstantAmmo 与 Projectile。
4. Summon 和实体管理器。
5. Equipment 与 Fly 状态。

### 阶段四：规模化

1. 技能模板 Task 库。
2. 模式表合并与效果器。
3. 一站式编辑器和依赖预览。
4. 数据 Lint、循环引用、Tag 所有权检查。
5. 网络延迟与性能自动化测试。

## 10. 编辑器必须提供的校验

- ID 唯一和引用闭包。
- AbilityTag、EffectTag、BuffID 命名规范。
- AbilityItem 必须有 GrantedAbility。
- InlineConfig 类型与 GrantedAbility 模板匹配。
- LocalPredicted Ability 必须有预测副作用声明。
- Infinite Buff 必须有移除条件。
- Buff 链无环。
- Stack Override 字段完整。
- Timeline 长度、Section、Montage 映射一致。
- Authority Notify 不允许放 Cosmetic 轨。
- Scope 形状字段合法。
- Projectile 反弹/穿透次数和递归上限。
- Summon 数量与 Owner 销毁策略。
- 模式效果器冲突和优先级。
- CueTag 有合法资产或明确允许缺失。
